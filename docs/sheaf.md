# Формат сцены Sheaf

Sheaf — бинарный файл с объектами сцены. Внутри лежат таблицы, по одной на архетип: строка таблицы —
объект, колонка — поле компонента. Файл описывает себя сам: имена компонентов и полей, их типы и
дефолты записаны в нём же, поэтому его может прочитать и показать программа, которая ничего не знает
о движке. **Смысл байтов определяет только файл**: читателю не нужны ни реестр компонентов, ни
дефолты из кода.

Расширение — `.sheaf`. Все числа little-endian. Значения не выровнены.

`Engine::SaveScene` пишет `scene.sheaf` рядом с `scene.json` (см. [`ARCHITECTURE.md`](ARCHITECTURE.md),
раздел о сценах). Читатель формата есть (`sheaf::Read`), но движок им сцену пока не грузит: она
грузится из `scene.json`.

---

## Файл

| что | размер |
|---|---|
| сигнатура: буквы `SHEF` в ASCII | 4 байта |
| число строк | u32 |
| строки | по каждой: длина u32, затем байты UTF-8 без завершающего нуля |
| число таблиц | u32 |
| таблицы | подряд |

Каждая строка файла — имя компонента, поля или ассета — лежит в нём один раз. Везде дальше на неё
ссылается **номер строки**: её позиция в этом массиве, с нуля.

## Таблица

Сначала идёт весь заголовок таблицы, потом данные всех её полей.

| что | размер |
|---|---|
| `rows` — число объектов | u32 |
| число компонентов | u32 |
| заголовки компонентов | подряд |
| данные полей | подряд, в порядке заголовков: компонент за компонентом, поле за полем |

Заголовок компонента — номер строки с именем (u32), число полей (u32) и заголовки полей. У тега
(`ShadowCaster`, `EditorHidden`, …) полей ноль, данных у него нет.

Набор компонентов таблицы и есть её архетип. Двух таблиц с одинаковым набором в файле нет.

## Поле

| что | размер |
|---|---|
| номер строки с именем | u32 |
| тип | u8 |
| флаги | u8 |
| способ записи | u8 |
| дефолт | размер значения по типу; у поля-списка отсутствует |

| код | тип | размер значения |
|---|---|---|
| 0 | `f32` | 4 байта |
| 1 | `u32` | 4 байта |
| 2 | `i32` | 4 байта |
| 3 | `u8` | 1 байт |
| 4 | `bool` | 1 байт, 0 или 1 |
| 5 | `str` | 4 байта, номер строки |
| 6 | `ref` | 4 байта, сквозной номер объекта (см. «Ссылки между объектами») |

Флаги говорят, как значения разложены по объектам:

| бит | значит |
|---|---|
| 0 | **список**: у каждого объекта своё число значений |
| 1 | **nullable**: значение может отсутствовать |
| 2–7 | не заняты, пишутся нулями |

Дефолт — значение, которое получает объект, если способ записи его значение пропустил (способ 2).
Он лежит в файле, а не берётся из кода, по двум причинам: файл без движка остаётся полным, и старая
сцена не меняется, когда в коде поменяли дефолт компонента.

## Данные поля: способы записи

Способ записи выбирает писатель, читатель обязан понимать любой из них. Все способы дают одно и то
же: по значению (или по списку значений) на каждый из `rows` объектов.

### 0 — все подряд

| флаги | данные |
|---|---|
| 0 | `rows` значений |
| список | `rows` длин (u32), затем все значения всех списков подряд, по объектам |
| nullable | битмап, затем только присутствующие значения |
| список + nullable | `rows` длин, битмап по всем элементам списков, затем только присутствующие элементы |

Битмап — по биту на значение, `ceil(n / 8)` байт. Значение `i` отвечает биту `i % 8` байта `i / 8`,
младший бит первый. 1 — значение присутствует и записано, 0 — отсутствует и не записано.

### 1 — одно на всех

Одно значение, записанное способом 0 для одного объекта (у списка — длина и его элементы). Это
значение получают все `rows` объектов.

### 2 — отметки

Только для поля без флагов. Сначала `ceil(rows / 8)` байт отметок, по биту на объект в том же
порядке, что у битмапа. 1 — у объекта своё значение, 0 — у объекта дефолт из заголовка поля. Затем
свои значения подряд, по объектам с отметкой 1.

```
10 объектов, своё значение у объектов 1, 8 и 9:

[ 0000 0010 ] [ 0000 0011 ] [ v1 ] [ v8 ] [ v9 ]
  объекты 0–7   объекты 8–9
```

### 3 — таблица уникальных

| что | размер |
|---|---|
| `K` — число различных значений | u32 |
| ширина номера: 1, 2 или 4 | u8 |
| различные значения | `K` значений, записанных способом 0 как для `K` объектов |
| номера | `rows` номеров указанной ширины, каждый меньше `K` |

Объект получает значение под своим номером. У поля-списка различное значение — список целиком.

Писатель берёт для каждого поля самый короткий способ: так поле, одинаковое у всех, уходит в одно
значение, поле с дефолтом у большинства — в отметки, а повторяющиеся имена и списки — в таблицу
уникальных.

## Ссылки между объектами

Идентификаторов объектов в файле нет. Поле, которое ссылается на другой объект (`Parent.parent`),
имеет тип `ref` и хранит **сквозной номер строки**: таблицы нумеруются по порядку в файле, строки
внутри — подряд, и объект `r` таблицы `t` имеет номер «сумма `rows` предыдущих таблиц + `r`».
Загрузка переводит эти номера в сущности после того, как создала все объекты. Отдельный тип, а не
`u32`, нужен, чтобы ссылку узнал читатель, ничего не знающий о компонентах: вьювер делает её
переходом к объекту.

## Запись из движка

Писатель формата — `sheaf::Writer` (`src/sheaf/`, отдельная цель `Sheaf`, которая не зависит от
движка): ему отдают таблицы колонками, способы записи он выбирает сам. Значение любого типа в
колонке — его 32 бита (`sheaf::Bits` для `f32`, номер из `Writer::Intern` для `str`), поэтому
равенство при выборе способа побитовое само собой.

Колонки из ECS собирает `ObjectManager::SaveSceneSheaf`: таблица на архетип, архетипы и компоненты
отсортированы по имени, как в `scene.json`; архетипы с `GeneratedComponent` не пишутся. Колонки
компонента делает `ComponentSpec::SaveSheaf` по схеме полей: вычисляемые поля пропускаются, `Angle`
пишется как `f32`, `AssetModel` — как `str`, а дефолт поля читается из строки, которую создаёт
`add_default`, — того же `T{}` или прокси, что и у рантайм-создания. Компонент, схемой не
выразимый, задаёт `custom_save_sheaf`.

Так устроен `Renderable`: части сущности — элементы списков.

| поле | тип | на объект |
|---|---|---|
| `visible`, `alpha`, `flags`, `model` | `bool`, `f32`, `u32`, `str` | одно значение |
| `mat_lod0` … `mat_lod3` | список `str`, nullable | материал каждой части на уровне; пусто — часть на уровне не рисуется или уровня у модели нет |
| `state_part`, `state_role`, `state_value` | списки `u32` | по элементу на состояние варианта: номер части, роль, значение |

Колонки уровня, на котором ни у одного объекта нет материала, в файле нет; колонок состояний нет,
если состояний нет ни у кого.

## Чтение

`sheaf::Read` (`src/sheaf/SheafReader.cpp`) принимает байты файла и возвращает массив строк и
таблицы в том же виде, в каком их принимает писатель: колонки раскрыты обратно, по значению или
списку на объект, отметки заменены дефолтом, номера таблицы уникальных — самими значениями.
Отсутствующая ячейка nullable хранит 0, значение `str` — номер в массиве строк файла. К каждой
колонке читатель добавляет, как она лежала в файле: способ записи и число байт данных — это то,
что показывает вьювер.

**Прочитанное, отданное писателю, даёт тот же файл байт в байт**, если сначала передать писателю
строки файла по порядку (`Writer::Intern`): номера строк совпадут, а способ записи писатель
выбирает по данным, которые не изменились.

Ошибка — текст с номером таблицы и именем поля (`таблица 2, Transform.x: …`); дальше файл не
разбирается:

- нет сигнатуры, файл обрывается раньше, чем кончаются заявленные данные, или после последней
  таблицы остались байты;
- неизвестный тип, способ записи или занятый свободный бит флагов — размер такого поля не вычислить;
- способ 2 у поля с флагами;
- номер строки за пределами массива строк — в имени, дефолте или значении `str`;
- ширина номера не 1, 2 или 4, или номер в таблице уникальных не меньше `K`.

Каждое число, за которым следуют записи, сверяется с остатком файла до того, как под него выделена
память: мусорный счётчик даёт ошибку, а не многогигабайтную аллокацию. Единственное исключение —
`rows` поля со способом 1: одно значение законно раскрывается на любое число объектов.

## Вьювер

`SheafView` (`src/sheaf/viewer/`) — отдельная программа, которая линкует только `Sheaf`, ImGui и SDL:
файл любой игры открывается без движка. Слева таблицы, в центре сетка выбранной (колонки
сгруппированы по компонентам, компонент скрывается галочкой), внизу выбранный объект целиком или
выбранная ячейка: тип, дефолт, способ записи, размер, элементы списка.

| что | как показано |
|---|---|
| номер объекта | сквозной, как в полях `ref` |
| значение, равное дефолту | серым |
| `str` | текстом; пустая строка — `""` |
| отсутствующее значение nullable | серым `—` |
| список | `[n]` в сетке, элементы — в панели выбранного |
| `ref` | ссылкой: клик открывает таблицу объекта и прокручивает к нему |

Сортировка — кликом по заголовку; `str` сортируется по тексту, списки не сортируются. Фильтр —
«поле = значение», у списка подходит строка, где равен хотя бы один элемент; `—` ищет пустые
ячейки nullable. Сортировка и фильтр не переставляют данные: `Model` держит порядок показа
(номера строк), а сетка рисует через `ImGuiListClipper` только видимые строки, поэтому размер
таблицы на кадр не влияет. Кадр рисуется только после ввода, в покое вьювер спит в `SDL_WaitEvent`.

## Diff в git

Сам по себе `.sheaf` для git бинарный (в нём есть нулевые байты), и `git diff` пишет только
`Binary files … differ`. Читаемый diff даёт механизм git `textconv`: перед сравнением git прогоняет
обе версии файла через указанную программу и сравнивает её текстовый вывод построчно. В репозитории
по-прежнему лежит бинарный файл, текст живёт только на время diff.

Программа — `SheafDump` (`src/sheaf/dump/`, линкует только `Sheaf`): `SheafDump файл.sheaf` печатает
в stdout строку-заголовок на объект и под ней по строке на поле:

```
Renderable+Transform 0
	Renderable.model = "building30"
	Renderable.mat_lod1 = ["building", "building_glass", —, "telecom"]
	Transform.x = 1
```

| что | как напечатано |
|---|---|
| объект | имена компонентов через `+` и номер строки **в своей таблице** |
| `f32` | кратчайшая запись, которая читается обратно в те же биты; `-0` отдельно от `0` |
| `str` | в кавычках, `"`, `\` и управляющие символы экранированы |
| отсутствующее значение nullable | `—` |
| `ref` | `-> Таблица строка` |

Сквозных номеров в выводе нет: они сдвигаются от правки любой таблицы выше по файлу, и в diff
поменялся бы каждый следующий объект. Заголовок объекта начинается с буквы, а поля — с табуляции,
поэтому git ставит заголовок в строку `@@ … @@` ханка, как имя функции в коде. Способ записи
полей и дефолты не печатаются: diff показывает только изменения значений, а не то, как писатель
их упаковал.

Настройка из двух частей. `.gitattributes` в репозитории игры (`games/`) коммитится и говорит, что
`.sheaf` сравнивается драйвером `sheaf`:

```
*.sheaf diff=sheaf
```

Что этот драйвер запускает, git из репозитория брать не позволяет (иначе клон мог бы заставить
запустить что угодно), поэтому **каждый клон прописывает конфиг сам**, один раз:

```
git config diff.sheaf.textconv "C:/…/games/build/xor_engine/src/sheaf/dump/Debug/SheafDump.exe"
git config diff.sheaf.cachetextconv true
```

Без конфига diff остаётся `Binary files … differ`, ничего не ломается. Текст в десятки раз больше
файла (сцена 16 КБ — 1.2 МБ текста), поэтому включён кэш: git сохраняет вывод для каждой версии
файла, уже записанной в git (коммит, индекс), в `refs/notes/textconv/sheaf` и для неё `SheafDump`
больше не запускает. Файл в рабочей копии в кэш не попадает и дампится при каждом diff. Веб-интерфейс GitHub чужих программ не
запускает и показывает файл бинарным; textconv работает в локальном git и клиентах поверх него.
`textconv` влияет только на показ: при слиянии конфликтная сцена выбирается целиком.

## Чтение в движок

Загрузки сцены из Sheaf в движке пока нет. Колонки будут сопоставляться с полями компонентов
**по именам** компонента и поля, а не по позиции:

- поля из реестра нет в файле — объект получает дефолт из кода;
- поля из файла нет в реестре — оно пропускается.

## Инварианты и грабли

- **Заголовок таблицы стоит перед её данными**, а способ записи поля — в заголовке. Писатель
  выбирает способы до того, как пишет заголовок, то есть держит данные таблицы в памяти целиком.
- **Сравнение значений побитовое.** Способы 1–3 решают, равны ли два значения. Для `f32` это
  сравнение битов, а не `==`: иначе `-0.0` склеится с `0.0` и знак пропадёт, а NaN никогда не
  совпадёт сам с собой.
- **Значения не выровнены.** Читать их через `memcpy`, а не приведением указателя в буфер.
- **Пропуски ломают прямой доступ.** У способов «все подряд» без флагов и «одно на всех» значение
  объекта `r` находится сразу. У nullable, списков и отметок до него нужно досчитать: длины или
  единицы в битмапе предыдущих объектов.
- **Дефолт из заголовка пишется всегда**, даже если способ его не использует: по нему вьювер
  показывает, какое значение у поля обычное.
- **Сквозные номера ссылок зависят от порядка таблиц и строк.** Писатель, который переставит
  таблицы или строки, обязан пересчитать все поля-ссылки.
- **Кэш textconv не знает о версии `SheafDump`.** Git сбрасывает кэш, только когда меняется строка
  `diff.sheaf.textconv`. После правки формата вывода старые версии сцены показываются старым
  текстом и дают ложный diff против новых; сбросить кэш —
  `git update-ref -d refs/notes/textconv/sheaf`.
