# Данные инстанса: строки, PIB, out_pib, разреженные каналы

Вершинный шейдер получает от GPU одно число — `SV_InstanceID`. Всё остальное он должен найти сам,
и путь у него такой:

```
SV_InstanceID  ->  OutPib[id]  ->  row  ->  ModelMatrixBlock[row], InstanceDataBlock[row], ...
```

Уровней адресации три, и каждый решает свою задачу: **строка** — где лежат данные сущности,
**PIB** — какая сущность стоит за этой записью отрисовки, **out_pib** — кто из них пережил отсев.
Поверх этого работают **разреженные каналы** — для данных, которые есть у малой доли сущностей.

---

## Строка

Строка — это позиция сущности в наборе **параллельных буферов**: у всех у них одна длина, один
порядок и один смысл индекса. По строке лежат трансформ, инстанс-данные (`alpha`, `flags`),
ограничивающая сфера, биты канала состояний.

Домен строк — сущности с `Positions` и `DrawComponent`, в порядке архетипов, а внутри архетипа — в
порядке сущностей:

```
row = render_instance_base(архетип) + индекс сущности в архетипе
```

**Все буферы, индексируемые строкой, обязаны строиться одним и тем же обходом с одним и тем же
отбором.** Это главный инвариант этой части движка, и нарушается он тихо: разъехавшийся порядок
даёт объекту чужую матрицу, чужую сферу или чужой вариант текстуры — без краша, без лога и без
единого симптома, кроме неправильной картинки.

У сущности, которая рисуется, но строки не имеет (нет `Positions`), строки нет и в этих буферах:
такой шейдер строит позицию сам — например, скайбокс выводит её из камеры.

---

## PIB — вход отсева

Дерево батчей раскладывает сущности по проходам, шейдерам, атласам, текстурам и моделям. Одна
сущность попадает в столько батчей, сколько раз она рисуется за кадр, и на каждое такое попадание
приходится одна **запись PIB**. Значение записи — строка её сущности.

Порядок записей — это обход дерева батчей, и он произвольный относительно ECS. Тем же обходом
пишется `EntityToCmd` (запись -> индекс команды в своём проходе), поэтому две таблицы совпадают
запись в запись.

Значение `-1` в PIB значит «строки нет»: сущность без трансформа либо запись протухшего слота.
Записывается именно `-1`, а не пропуск записи — пропуск сдвинул бы все последующие записи
относительно `first_instance` команд. Этот же `-1` понимают оба читателя: шейдер отсева скаттерит
такую запись безусловно, вершинник видит отрицательную строку и ничего не читает.

Строка кэшируется в самой записи вместе с идентификатором сущности, и заливка её обычно только
читает. Перезаписываются все строки ровно тогда, когда меняется состав сущностей: тогда едут и
базы архетипов, и индексы внутри них, и старая строка не годится никому — включая тех, кого правка
не касалась, потому что удаление переносит чужую сущность на освободившийся индекс.

## out_pib — выход отсева

`out_pib` — компактный результат: шейдер отсева кладёт выживших **подряд** в кусок, отведённый их
команде, а адрес куска берёт из `first_instance` самой команды. Поскольку
`SV_InstanceID = first_instance + i`, вершинник индексирует буфер напрямую:

```hlsl
int row = OutPib[input.instanceID];
```

Никакой арифметики блоков и камер в вершиннике нет — она вся ушла в адрес, записанный в команду
(см. [`culling.md`](culling.md)).

Разница между двумя буферами: **PIB индексируется записью батча, `out_pib` — слотом команды**.
Первый — что мы собирались рисовать, второй — что рисуем.

Отрицательная строка на выходе означает, что запись пришла из безусловного скаттера (объект без
геометрии) либо не имеет строки вовсе. Вершинник обязан это проверить:

```hlsl
if (row < 0) {
    output = (VSOutput)0;
    output.position = float4(2.0, 2.0, 2.0, 1.0);   // все вершины за одной clip-плоскостью
    return output;
}
```

Позицию нужно записать даже здесь: голый `return` оставил бы `SV_Position` неопределённым.
Вырожденная позиция уводит примитив целиком за отсечение, и фрагментов он не даёт.

## Что читает вершинник

Общая часть у всех вершинников одна: строка из `out_pib`, матрица и инстанс-данные по строке.
Дальше начинаются различия, и они показывают, зачем нужен именно такой набор буферов:

- **Основной проход** передаёт строку во фрагментник отдельным `nointerpolation`-полем. Сам
  вершинник буфер состояний не читает: он общий с чужими шейдерными программами — теневыми,
  игровыми, — и каждая из них была бы обязана биндить этот буфер только потому, что он объявлен в
  общем вершиннике.
- **UI** обходится без `view`/`proj`: трансформ у UI-элемента экранный и даёт clip напрямую,
  а модель — единичный квад, который матрица раскладывает в нужный прямоугольник NDC.
- **Сплат** рисуется командой с одним индексом, поэтому вершинник запускается ровно раз на инстанс
  и геометрию не читает вовсе — только строку, матрицу и камеру.

## Разреженный канал: биты вместо поля

Часть данных есть у малой доли строк — переключённый вариант текстуры, текст на UI-элементе.
Полноразмерный массив по домену строк платил бы своей шириной за значение «ничего нет»: смещение
в 32 бита на строку — это мегабайты на сцену, из которых почти всё нули.

Канал устроен иначе. На строку остаётся **один бит присутствия**, а данные лежат компактно — по
одному элементу на носителя. Адрес элемента даёт **rank**: число носителей до этой строки.

Считается rank за O(1), без поиска. Биты режутся на слова по 32, и у каждого слова рядом лежит
префикс-popcount — сколько носителей было до него:

```hlsl
const uint  b = uint(row) & 31u;
const uint2 w = Words[uint(row) >> 5u];        // x = биты 32 строк, y = носителей до слова
if (((w.x >> b) & 1u) == 0u) return -1;        // не носитель
return int(w.y + countbits(w.x & ((1u << b) - 1u)));
```

Биты и префикс лежат **в одном буфере**, парой. По отдельности они не бывают валидны — префикс это
бегущая сумма по тем же битам, — и раздельные буферы разрешали бы залить одно без другого, получив
молча неправильные rank. Слитая пара этого не разрешает, читается одной загрузкой из одной
кэш-линии и экономит бинд в общих прологах, где каждый буфер обязана биндить каждая программа.

Цена на горячем пути: строка-не-носитель отвечает одной загрузкой и ветвлением, а таких строк
подавляющее большинство; вторая загрузка — уже в данные — достаётся только носителям. Памяти при
этом уходит 2 бита на строку вместо 32.

Отрицательная строка даёт `-1` естественным образом, поэтому объекты без трансформа проходят через
канал без отдельной проверки.

Шейдерная половина — макрос `SPARSE_CHANNEL(NAME, регистр, space)`: он объявляет буфер слов и
функцию `NAME##Rank(row)`. Канал даёт **только адресацию**; буфер с самими данными объявляет
вызывающий, потому что раскладка данных у каждого канала своя. CPU-половина — `SparseRankChannel.h`,
и раскладка слова продублирована в обеих: `x` — биты, `y` — префикс.

### Каналы, построенные на этом

| канал | буферы | чем индексируется |
|---|---|---|
| состояния вариантов текстур | `rank` (слова) · `index` (смещение ячеек носителя) · `state` (ячейки, по секции на материал сущности) | `rank` — строкой, `index` — рангом, `state` — смещением из `index` |
| текст UI | `rank` (слова) · `index` (`{offset,count}`) · `text` (коды глифов подряд) | так же; `offset/count` режут пул глифов на срез элемента |

Фрагментник читает канал одинаково: взял строку, спросил rank, при `rank >= 0` прочитал `index` и
по нему — данные.

Все буферы канала обслуживает **один модуль**, и это обязательно: rank даёт номер носителя, index
по этому номеру даёт смещение, по которому данные положила третья заливка. Согласовать три
проекции может только один и тот же обход в одном и том же порядке — разведи их по модулям, и
разъезд даст чужие данные, снова без краша и без лога.

Гейты у буферов канала при этом **разные**, и это следствие того, что попадание в канал и значение
в нём меняются от разных вещей. Присутствие и смещения зависят от структуры — от порядка строк, от
наличия тега, от числа материалов сущности, — и гейтятся ревизией батчей послотно. Сами значения
структуру не меняют намеренно: переключение варианта не трогает дерево батчей, поэтому ни один
структурный сигнал его не видит, и буфер значений льётся каждый кадр. Дёшево это потому, что домен
отфильтрован тегом на входе в обход.

Список носителей подаётся **по возрастанию строки** — это то, что делает `rank` бегущей суммой.
Обход по архетипам и локальным индексам выдаёт такой порядок сам, без сортировки. Полного массива
слов на CPU при этом не держат: слово без носителей — это ровно `{0, сколько их было до него}`,
поэтому поток слов строится на лету.

## Инварианты

- **Все буферы, индексируемые строкой, строятся одним обходом с одним отбором.** Разъезд не
  падает и не логируется — он рисует чужие данные.
- **Отсутствие строки пишется значением `-1`, а не пропуском записи.** Пропуск сдвинул бы
  адресацию всех последующих записей.
- **Вершинник записывает `SV_Position` и на отсечённом инстансе.**
- **Раскладка слова канала продублирована в C++ и HLSL** и обязана совпадать.
- **Носители подаются по возрастанию строки.**
- **Буферы одного канала обслуживает один модуль**, потому что согласовать их может только общий
  обход.
