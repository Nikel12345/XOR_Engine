# Отсев и компактация

Отсев идёт целиком на GPU, в вычислительной стадии кадра. Для каждой PIB-записи проверяется,
видна ли она камере, и выжившие укладываются **подряд** в выходной буфер `out_pib`, а число
инстансов набирается атомарно прямо в indirect-командах. CPU в решении не участвует: он готовит
входные буферы и раскладку, а после стадии ничего не читает обратно.

Слоты, слепки и стадии кадра — в [`frame.md`](frame.md); что такое PIB, `out_pib` и строка
трансформа — в [`instance-data.md`](instance-data.md); откуда берутся сами команды —
в [`batches.md`](batches.md).

---

## Раскладка индиректа и out_pib

Оба буфера нарезаны на **регион на проход** (порядок регионов = порядок проходов), а внутри
региона — на **блок на каждый дроу прохода за кадр**. В блоке лежат только команды своего прохода:

```
индирект: [ shadow: L x 10 ][ main: 1 x 12 ][ transparent: 1 x 2 ][ debug: 1 x 0 ][ UI: 1 x 2 ]
out_pib:  [ shadow: L x 22 ][ main: 1 x 23 ][ transparent: 1 x 5 ][ debug: 1 x 0 ][ UI: 1 x 2 ]
```

Размер каждого буфера — сумма `blocks * commands` по проходам. Камера рисует только свои проходы,
поэтому в блоке теневой камеры лежат теневые команды, и ничего больше. Пустой проход даёт нулевой
вклад: префиксная сумма переступает через него, его база совпадает с базой следующего, и это
безвредно — нулевой регион никто не разыменовывает.

В `first_instance` каждой команды лежит **абсолютный** адрес её куска в `out_pib`:

```
first_instance = pib_base(прохода) + номер_блока * pib(прохода) + локальное_смещение
```

`SV_InstanceID = first_instance + i`, поэтому вершинные шейдеры читают просто
`OutPib[instanceID]`, без арифметики блоков. Это же число читает скаттер, когда кладёт выжившую
запись, — адрес живёт в одном месте, в самой команде.

## Кто что решает

**`PassManager`** владеет проходами и их порядком, поэтому владеет и раскладкой. `StampRegions`
штампует регионы слота, `AskRegions(slot)` отдаёт штамп всем потребителям. Базы регионов
считаются только здесь, одним проходом по проходам.

Проход заявляет о себе **только число блоков**, инструкцией `CreateRegionCountInstruction`,
зарегистрированной рядом с его созданием. Границы назвать ему нечем, и в этом весь смысл: что бы
инструкция ни вернула, покрытие останется непересекающимся. Проход, не зарегистрировавший её,
получает один блок.

Дальше раскладку **исполняют**, а не пересчитывают:

| кто | что делает |
|---|---|
| `BatchBuilder` | нумерует команды **локально для прохода** — счётчик свой у каждого |
| `PIB_DataModule::StoreEntityToCmd` | та же нумерация плюс упаковка диапазона размеров |
| `IndirectDataModule` | пишет команды пасс-мажорно, ставит абсолютный `first_instance`; гейт заливки — пара «ревизия батчей + штамп регионов» на слот |
| `PassManager::RenderPassStandardBody` | тело прохода передаёт номер своего блока, байтовое смещение в индиректе считает менеджер по штампу |

Наружу байты не отдаются, чтобы не появился второй способ их посчитать. Если тело прохода
запросило блок за пределами заявленного числа, в лог уходит имя прохода и оба числа, но дроу
выполняется: иначе рассинхрон выглядел бы как «проход просто не рисуется».

Гейт индиректа стоит на двух вещах, потому что содержимое команд зависит от обеих: команды берутся
из дерева батчей (ревизия), а их размещение — из раскладки регионов, которая меняется и без
пересборки дерева (добавили теневой свет, сняли `ShadowCaster`). Покадрово в буфере меняется только
`num_instances`, и его обнуляет GPU.

## Проход отсева

`CULLING_PASS` состоит из compute-программ, и порядок их создания определяет порядок исполнения
(см. `../../WARNINGS.md`).

**Первой создаётся `culling_clear`** — она обнуляет `num_instances` у всех команд всех регионов.
Это обязательно каждый рендер: скаттер набирает `num_instances` атомарно, а заливка с нулями идёт
только в prepare. Рендер-поток может отрисовать один и тот же слот повторно, без нового prepare
(см. fallback в [`frame.md`](frame.md)), и тогда без сброса счётчики накопились бы поверх старых —
одна строка попала бы в несколько слотов `out_pib`, то есть объекты нарисовались бы копиями друг
друга. SDL ставит барьер между compute-пассами одного командного буфера, поэтому скаттер видит уже
нули.

**Дальше — скаттер, по программе на проход.** Все они создаются одним локальным
`CreateCullingProgram` и отличаются только именем, камерным буфером и тем, участвует ли проход в
отсеве по размеру. Числа своего региона программа берёт из штампа по ординалу прохода, размер
диспатча — это `pib` региона (нет блоков — нет и работы).

Один вызов шейдера обрабатывает одну PIB-запись:

1. `PIB[i]` даёт строку трансформа (`-1` — записи без трансформа);
2. слово `EntityToCmd[i]` даёт локальный индекс команды и две ступени диапазона размеров;
3. сфера берётся из `BoundSpheres[row]`, переводится в мир трансформом строки, радиус масштабируется
   максимальным из масштабов по столбцам матрицы;
4. цикл по блокам региона: для блока `b` тестируется `Cameras[b]` — фрустум, затем экранный размер;
5. выживший скаттерится: `InterlockedAdd` по `num_instances` команды `cmd_base + b*commands + k`
   выдаёт слот, `first_instance` той же команды даёт адрес, и строка ложится в `out_pib`.

## Отсев по экранному размеру

Поверх фрустума работают два независимых порога, оба — про радиус ограничивающей сферы в пикселях
приёмника. Они про разное и потому не заменяют друг друга, а **складываются по максимуму**.

**Глобальный порог прохода** `min_screen_radius_px` — единственное настроечное поле блоба
`CullingPibUniform` (остальные переписываются каждый кадр из региона), поэтому у состояния прохода
есть схема `CULLING_STATE` и порог правится из редактора. Он отсеивает пыль: то, что мельче порога,
не скаттерится вовсе и не рисуется никак.

Порог один на все программы, но применяет его только та, которой дан цветовой таргет прохода
(`target_height`). У теней и UI своё разрешение, и тот же порог в пикселях означал бы там совсем
другой размер объекта; кому таргет не дан, у того отсев выключен локально.

**Собственный диапазон сабмеша** `screen_size_span` — про неразрешимую деталь, а не про пыль. Две
ступени по 4 бита едут в старших битах слова `EntityToCmd` (младшие 24 — индекс команды), ступень
разворачивается в пиксели как `0.5 * 2^(level-1)`. Ступень `0` означает «граница не задана» и даёт
`0` снизу / бесконечность сверху, поэтому сабмеш без проставленного диапазона ведёт себя так, будто
поля нет вовсе.

Верхняя граница — это место, которое сабмеш уступает более грубому уровню: уровни модели лежат
соседними сабмешами с непересекающимися диапазонами, и видимым остаётся ровно один.

Экранный радиус считается так:

```
w  = dot(vp[3], float4(center, 1))          // расстояние вдоль оси взгляда
px = radius * proj[1][1] * (height/2) / w
```

`radius/w` вместо `radius/sqrt(w^2-r^2)` — приближение, точное ровно там, где оно важно: у мелочи
`w >> r`. Считать его можно только для записей, **прошедших фрустум**, иначе `w` может оказаться
неположительным.

Диапазоны приходят из манифеста сцены (`screen_size_span` в `models.json`) — это настройка, а не
свойство геометрии в `.bin`, и правится она через `ModelManager::SetSubmeshSpan`. Ступени попадают
в слово `EntityToCmd` из **копии**, снятой батчем на сборке дерева, поэтому правка диапазона обязана
пересобрать батчи — тот же инвариант, что у скопированного UVL текстуры.

**Обратная сторона порога.** Флаг `invert_span` заставляет проход рисовать то, что **ниже** нижней
границы сабмеша, вместо того, что внутри диапазона. Обе стороны получаются из одной пары ступеней,
поэтому порог живёт в одном месте, а какую его сторону взять — решает проход; двух чисел, обязанных
совпадать, здесь не заводится. На этом устроен сплат-путь: у объекта две записи (`BatchBuilder`
заводит их по одной на sp материала), и два отсева независимо решают каждый про свою, взаимно
дополнительными тестами — проходы друг о друге не знают. Сам сплат-проход и его culling-программа
сейчас не регистрируются; механизм включается одной строкой.

Для прохода с `invert_span` глобальный порог означает абсолютный пол, ниже которого не рисуется
ничего, и он обязан стоять ниже границы сабмеша — иначе срежет сплаты вместе с оригиналами.

## Что не отсекается

Три случая идут одним путём — сферой-заглушкой с `w < 0`, которую скаттер трактует как «геометрии
нет» и скаттерит безусловно во все блоки прохода:

- **записи без трансформа** (`row < 0`) — строки, а значит и сферы, у них нет; в `out_pib` уезжает
  `-1`, и вершинный шейдер такой записи позицию строит сам, не читая буфер;
- **модель без геометрии** — сфера модели считается объединением сфер её сабмешей, а при их
  отсутствии вырождается;
- **UI** — `BoundSphereDataModule` пишет `w < 0` всем архетипам с `UIComponent`: UI живёт в NDC,
  его трансформ экранный, и мировой фрустум мис-каллил бы его. Камерный буфер программы отсева UI
  из-за этого фактически не читается.

## Инварианты и грабли

- **Инструкция счёта регионов читает слепки слота** (`Ask*`), а не живое состояние, и её число
  обязано совпадать с числом дроу в теле прохода. Расхождение ловится логом в
  `RenderPassStandardBody`.
- **Вся адресная арифметика — сложения и умножения, ни одного вычитания.** Беззнаковое вычитание
  молчит и в шейдере, и на CPU: смещение куска от начала сегмента накапливается по ходу обхода,
  а не вычисляется вычитанием базы.
- **`culling_clear` — первая compute-программа `CULLING_PASS`.** Порядок создания и есть порядок
  исполнения.
- **Экранный размер считается только после фрустум-теста.**
- **Команда с нулём инстансов носит бессмысленный `first_instance`** — это нормально, GPU не
  заведёт ни одного инстанса, и валидировать тут нечего.
- **Порядок проходов для отсева не значим**, как и порядок регистрации инструкций: слепки пишет
  своя фаза кадра. Единственный порядковый инвариант — внутри `CULLING_PASS`.
- Цена пер-проходной раскладки — диспатч на проход: мелкие проходы дают микро-диспатчи, пустые
  пропускаются. Это размен на независимость проходов друг от друга.
