# Уровни детализации

Уровень детализации — это другая геометрия и другие материалы, которыми объект рисуется, когда
занимает на экране мало места. Цепочка уровней принадлежит **модели**, материалы уровней —
**сущности**, а выбор уровня на кадр делает шейдер отсева по экранному радиусу объекта.

Как уровни раскладываются по командам — в [`batches.md`](batches.md); как выбирается уровень —
в [`culling.md`](culling.md).

---

## Цепочка уровней модели

`ModelData::lods` — список `ModelLod`, по элементу на уровень начиная с первого; уровень 0 — сама
модель. Всего уровней вместе с нулевым не больше `MAX_MODEL_LODS` (4).

| поле `ModelLod` | смысл |
|---|---|
| `model` | модель уровня; может быть самой моделью — тогда геометрия та же, отличаются материалы |
| `switch_px` | экранный радиус в пикселях: пока объект меньше, предыдущий уровень уступает этому |

Пороги идут по убыванию: объект крупнее `lods[0].switch_px` рисуется уровнем 0, мельче — уровнем 1,
мельче `lods[1].switch_px` — уровнем 2 и так далее.

Задаётся цепочка через `ModelManager::SetModelLods` в двух видах:

- **путями** (`ModelLodSource{vertex_path, index_path, switch_px}`) — так её грузит манифест сцены.
  Уровень с путями самой модели ссылается на неё же. Остальные грузятся отдельной моделью с именем
  `<модель>#<уровень>` в пул модели и с её якорем; у такой модели тег `System`, и в манифесте
  отдельной записью она не появляется;
- **готовыми `ModelLod`** — для кода, у которого модели уровней уже есть.

`LevelCount(model)` отвечает, сколько уровней у модели вместе с нулевым, `LevelModel(model, L)` —
модель уровня `L`.

В `models.json` цепочка лежит в записи модели:

```json
{ "name": "tree", "vertex": "...", "index": "...", "anchor": 0, "pool": "",
  "lods": [ { "vertex": "...", "index": "...", "switch": 24.0 } ] }
```

Сфера для отсева у сущности одна на все уровни — объединение сфер моделей всех уровней: строка
трансформа у сущности одна, и тест видимости обязан быть верен при любом выбранном уровне.

## Материалы уровней на сущности

Рисуемую сущность описывает компонент `Renderable`:

| колонка | смысл |
|---|---|
| `visible` | попадает ли сущность в дерево батчей |
| `alpha`, `flags` | инстанс-данные строки |
| `model` | модель уровня 0; остальные уровни берутся из её цепочки |
| `materials` | по `MaterialSlot` на **часть** |

Часть — это номер `SubMeshData::material_index`. Номера частей общие для всех уровней: модели
уровней обязаны договориться, какая часть что означает. У `MaterialSlot` материал на каждый уровень
(`per_lod[MAX_LOD]`) и состояния вариантов текстур (`states`, см. [`materials.md`](materials.md)).
Пустой `per_lod[L]` значит, что часть на уровне `L` не рисуется.

Состояния вариантов у части одни на все уровни: секция в буфере состояний считается по номеру части
(`StateSection`), а набор вариативных ролей — по материалу уровня 0. Поэтому материалы уровней одной
части держат вариативные роли в том же составе, что и уровень 0.

Число частей подгоняет `EngineContext::FitRenderableParts`: частей столько, сколько номеров
встречается у сабмешей всех уровней, а ячейки уровней, где части нет, очищаются.

Правка идёт через `EngineContext`:

- `ChangeModel(entity, model)` — меняет модель, подгоняет части и поднимает ревизию сущностей
  (от модели зависит сфера);
- `ChangeMaterial(entity, material, part, level)` — ставит материал части на уровне; на уровне 0
  заодно сбрасывает состояния части.

Обе ставят сущность в очередь перестановки дерева батчей. Запись в компонент напрямую дерево не
обновит: модель и материалы в нём скопированы.

В `scene.json` колонка `materials` — строка на сущность, в строке список частей, в части — имена
материалов по уровням, `null` на пустом уровне:

```json
"materials": [ [ ["bark", "bark_far", null], ["leaves", "leaves_far", "leaves_dot"] ] ]
```

## Выбор уровня

Уровень выбирает `culling_scatter` для каждой записи PIB по **камере игрока** (`cameraBuffer[0]`) и
высоте цветового таргета сцены:

```
px = radius * proj[1][1] * (height / 2) / w
L  = 0;  while (L + 1 < lod_count && px < switches[L]) ++L;
```

Уровень один на все блоки прохода: теневая камера рисует тот уровень, который виден игроку, и тень
совпадает с объектом. Пороги (`switches`) и число уровней шейдер берёт из таблицы групп — их туда
копирует дерево батчей, поэтому правка цепочки модели пересобирает дерево.

Без отсева уровень не выбирается: команды уровня 0 заливаются с полным числом инстансов, остальные
с нулём, и каждый объект рисуется уровнем 0.

## Программы для плоских уровней

Дефолтный набор шейдеров содержит программы, которые рисуют дальний уровень дешевле самой модели.
Их берёт материал уровня.

| программа | проход | что рисует |
|---|---|---|
| `LOD_Quad` | основной | плоскую модель в плоскости XY, развёрнутую к точке камеры; от трансформа берутся перенос и средний по трём осям масштаб |
| `LOD_QuadShadow` | теневой | то же, развёрнутое к световой камере |
| `LOD_Splat` | основной | модель одной точкой в пиксель (топология — точки) |

Для `LOD_Quad` подходит модель `quad`, для `LOD_Splat` — модель `point` из одной вершины; обе есть в
дефолтных ресурсах. Выход вершинников совпадает с основным, поэтому фрагментник у них из `Lit`, и
материал уровня заполняется теми же параметрами и текстурами. Это вариант с `LIGHT_IGNORES_NORMAL`:
нормаль у обеих программ смотрит на камеру, поэтому диффузный свет в нём от нормали не зависит, и
объект освещён, с какой бы стороны ни стоял источник.

Плоскость `LOD_Quad` развёрнута к точке камеры: у соседних плоскостей наклон разный, и там, где они
перекрываются, равенство глубин сходится в линию. Порядок инстансов после отсева от кадра к кадру
свой, и плоскости, параллельные экрану, мерцали бы по всей площади перекрытия.
