# Отсев и компактация

Отсев идёт целиком на GPU, в вычислительной стадии кадра. Для каждой записи PIB выбирается уровень
детализации и проверяется, видна ли она камерам прохода. Выжившие укладываются **подряд** в
выходной буфер `out_pib`, после чего команды индиректа переписываются на их куски. CPU готовит
таблицы и раскладку и после стадии ничего не читает обратно.

Отсев необязателен. Индирект, залитый CPU, уже рисует каждый объект уровнем 0 по PIB (см.
[`batches.md`](batches.md)); отсев переписывает тот же буфер. Какой буфер записей читает
вершинник — PIB или `out_pib`, — задают бинды его шейдерной программы. Дефолтный набор биндит
`out_pib` и создаёт программы отсева вместе с остальными дефолтными программами.

Слоты, слепки и стадии кадра — в [`frame.md`](frame.md); что такое PIB, `out_pib` и строка
трансформа — в [`instance-data.md`](instance-data.md); группы и команды —
в [`batches.md`](batches.md); уровни детализации — в [`lod.md`](lod.md).

## Регионы и блоки

Индирект нарезан на **регион на проход** (порядок регионов = порядок проходов), а внутри региона —
на **блок на каждый дроу прохода за кадр**. Блок — это копия всех команд прохода для одной камеры:
теневой проход рисуется по разу на теневой свет, и блоков у него столько же.

```
индирект: [ shadow: L x 10 ][ main: 1 x 12 ][ transparent: 1 x 2 ][ debug: 1 x 0 ][ UI: 1 x 2 ]
```

**`PassManager`** владеет проходами и их порядком, поэтому владеет и регионами. `StampRegions`
штампует их на слот, `AskRegions(slot)` отдаёт штамп всем потребителям. Проход заявляет о себе
только число блоков — инструкцией `CreateRegionCountInstruction`, зарегистрированной рядом с его
созданием; проход без неё получает один блок. Базы регионов считаются только в `StampRegions`.

Регион есть у каждого render-прохода. Индирект, PIB, `out_pib` и счётчики раскладываются обходом
упорядоченного списка render-проходов (`PassManager::GetOrderedRenderPasses`), и место прохода в
этом списке — его **ординал** (`RenderPassStep::ordinal`), который выдаёт `FillRenderPasses`. По
ординалу адресуются все пер-проходные раскладки слота: штамп регионов, раскладка отсева, списки
рисования слепка. Откуда берётся порядок проходов — в [`passes.md`](passes.md).

Тело прохода передаёт номер своего блока, а байтовое смещение в индиректе считает
`PassManager::RenderPassStandardBody` по штампу. Если тело запросило блок за пределами заявленного
числа, в лог уходят имя прохода и оба числа, и дроу выполняется: так рассинхрон виден на экране.

Гейт заливки индиректа стоит на двух вещах: ревизии дерева батчей (из неё команды) и штампе
регионов (из него размещение). Регионы меняются и без пересборки дерева — например, когда
добавили теневой свет.

## Раскладка out_pib и счётчиков

`out_pib` и счётчики тоже нарезаны по проходам и блокам. Внутри блока у каждой группы прохода
**кусок на каждый её уровень**, размером с саму группу — столько записей уровень может получить в
худшем случае:

```
out_pib:   out_base(прохода) + b * out_cap + group.out_offset + L * group.size + слот
счётчик:   cnt_base(прохода) + b * gl_count + group.gl_base + L
```

- `out_cap` — сумма `size * lod_count` по группам прохода, размер блока в `out_pib`;
- `gl_count` — сумма `lod_count` по группам, число **групповых уровней** (пар «группа, уровень»);
- `out_offset`, `gl_base` — начало группы внутри блока в тех же двух раскладках.

Считает всё это `CullingDataModule`. Из дерева батчей он собирает три таблицы и раскладку
проходов, а на слот доставляет к ней блоки и базы регионов (`Stamp`):

| таблица | элемент | чем индексируется |
|---|---|---|
| `RecordGroup` | номер группы | записью PIB |
| `Groups` | `CullGroupEntry`: `size`, `out_offset`, `gl_base`, `lod_count`, `switches` | номером группы |
| `CmdGroupLevel` | `(группа << 2) \| уровень` | командой прохода |

Таблицы пересобираются по ревизии дерева и заливаются послотно. Размеры `out_pib` и буфера
счётчиков берутся из той же раскладки слота. `CullGroupEntry` продублирован в HLSL и обязан
совпадать с ним байт в байт.

## Проход отсева

`CULLING_PASS` состоит из compute-программ, и порядок их создания определяет порядок исполнения
(см. `../../WARNINGS.md`). `DefaultShaderProgramSet::SetCullingPrograms` создаёт первой
**`culling_clear`**, которая обнуляет все счётчики, и подключает к отсеву проходы тени, основной,
прозрачный, отладочный и UI.

Программы отсева одного прохода создаёт `DefaultShaderProgramSet::AddPassCulling`, подряд:

1. **`culling_scatter`** — раскладывает записи;
2. **`culling_fixup`** — переписывает команды.

Параметры прохода — его имя, камерный буфер (камера на блок) и признак прохода камеры игрока, в
котором отсекается мелочь. Числа своего региона программа берёт из раскладки слота по ординалу
прохода и читает ординал в момент исполнения. Пара пишет и читает только регионы своего прохода в
`out_pib`, счётчиках и индиректе, поэтому порядок исполнения задают два условия: `culling_clear`
идёт первой, scatter прохода — раньше его fixup. SDL ставит барьер между compute-пассами одного
командного буфера, поэтому каждая следующая программа видит результат предыдущей.

Сброс идёт на каждом вычислении слота: скаттер набирает счётчики атомарно, а тело буфера счётчиков
у каждого слота своё (`Dynamic`) и к следующему вычислению этого слота хранит итог прошлого.

### Скаттер

Поток на запись PIB прохода:

1. `PIB[i]` даёт строку трансформа, `RecordGroup[i]` — группу;
2. сфера берётся из `BoundSpheres[row]`, переводится в мир трансформом строки, радиус умножается на
   наибольший из масштабов по столбцам матрицы;
3. уровень `L` выбирается один раз по камере игрока (см. [`lod.md`](lod.md));
4. цикл по блокам прохода: для блока `b` тестируется `Cameras[b]` — фрустум, затем экранный размер;
5. выживший берёт слот `InterlockedAdd` по счётчику своего группового уровня в блоке и кладёт строку
   в `out_pib` по адресу из раскладки.

### Fixup

Поток на пару (блок, команда): `CmdGroupLevel` даёт группу и уровень команды, и команда получает
`first_instance` — начало куска этого группового уровня в `out_pib` — и `num_instances` — значение
его счётчика. Все команды уровня (по одной на сабмеш) рисуют один и тот же кусок.

Вершинник читает `OutPib[SV_InstanceID]`: `SV_InstanceID = first_instance + i`, и вся арифметика
блоков и групп уже лежит в адресе команды.

## Проход с геометрией

Render-проход рисует геометрию командами своего региона индиректа. Его участие складывается из
четырёх частей:

| часть | откуда берётся | у прохода без настройки |
|---|---|---|
| регион в индиректе, PIB, `out_pib` и счётчиках | обход списка render-проходов `PassManager` | есть всегда |
| число блоков | `PassManager::CreateRegionCountInstruction` | один блок |
| программы отсева | `DefaultShaderProgramSet::AddPassCulling` | отсутствуют, команды остаются в виде заливки CPU |
| буфер записей вершинника | бинды шейдерных программ прохода | в дефолтном наборе — `out_pib` |

Отсев прохода и бинды его программ согласованы между собой. Регион прохода в `out_pib` заполняет
scatter этого прохода, а fixup переписывает все команды региона индиректа на куски `out_pib`.
Поэтому программы отсеиваемого прохода биндят `out_pib`, а программы прохода без отсева — PIB, на
который указывают команды заливки CPU, и такой проход рисует каждую запись уровнем 0. Программа с
PIB в отсеиваемом проходе читает PIB по адресам кусков `out_pib`; программа с `out_pib` в проходе
без отсева читает пустой регион `out_pib`.

## Отсев по экранному размеру

Порог прохода `min_screen_radius_px` отсеивает пыль: запись, чей радиус в пикселях меньше порога,
не скаттерится и не рисуется. Это единственное настроечное поле состояния прохода
(`CullingState`), поэтому у него есть схема и оно правится из редактора.

Применяется порог только в проходе камеры игрока: у теней своё разрешение, и те же пиксели там
означали бы другой размер объекта.

Экранный радиус:

```
w  = dot(vp[3], float4(center, 1))          // расстояние вдоль оси взгляда
px = radius * proj[1][1] * (height/2) / w
```

`radius/w` — приближение `radius/sqrt(w^2-r^2)`, точное там, где оно нужно: у мелочи `w >> r`.
Считать его можно только для сфер перед камерой, иначе `w` неположителен: порог проверяется после
фрустума, а уровень выбирается только у записей с геометрией.

---

## Что не отсекается

Три случая идут одним путём — сферой-заглушкой с `w < 0`. Для скаттера это «геометрии нет»: запись
получает уровень 0 и скаттерится во все блоки прохода без тестов.

- **Записи без трансформа** (`row < 0`) — строки, а значит и сферы, у них нет; в `out_pib` уезжает
  `-1`, и вершинник такой записи строит позицию сам.
- **Модель без геометрии** — сфера модели считается объединением сфер её сабмешей и при их
  отсутствии вырождается.
- **UI** — `BoundSphereDataModule` пишет `w < 0` всем архетипам с `UIComponent`: UI живёт в NDC, и
  мировой фрустум отсёк бы его.

## Инварианты и грабли

- **Инструкция счёта регионов читает слепки слота** (`Ask*`), и её число обязано совпадать с
  числом дроу в теле прохода. Расхождение ловится логом в `RenderPassStandardBody`.
- **`culling_clear` — первая compute-программа `CULLING_PASS`, scatter прохода — раньше его
  fixup.** Порядок создания и есть порядок исполнения.
- **Отсеиваемый проход рисует программами с `out_pib`, проход без отсева — программами с PIB.**
- **Обходы групп и команд в `CullingDataModule` совпадают с `FinalizeOffsets`, `StorePIB` и
  `StoreIndirect`.**
- **Экранный размер считается только для сфер перед камерой.**
- **Тень рисует уровень, выбранный по камере игрока**, поэтому совпадает с объектом.
- Цена пер-проходной раскладки — диспатч на проход: мелкие проходы дают микро-диспатчи, пустые
  пропускаются.
