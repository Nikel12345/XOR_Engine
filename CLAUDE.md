# ЧИТАТЬ ПЕРЕД НАЧАЛОМ РАБОТЫ

Стойкие архитектурные правила проекта. Нарушать нельзя.

## Менеджеры не владеют друг другом

Менеджеры (`TextureManager`, `ModelManager`, `MaterialManager`, `ShaderManager`, `BufferManager`,
`CameraManager`, `FontManager`, `PassManager`, `PipeManager`, …) не хранят указателей друг на друга
и не вызывают друг друга. Это держит их листовыми: слои CMake (`EngineEcs`/`EngineGpu`/`Engine`)
не зацикливаются, а модуль физики линкует только часть из них.

Кроссменеджерская операция — метод `EngineContext` (он держит все менеджеры). Он передаёт чужие
менеджеры **параметрами** в листовой метод, и тот их не сохраняет:

```cpp
FontHandle* EngineContext::CreateFont(const std::string& name, const char* path, int px) {
    return font_manager->CreateFont(texture_manager, buffer_manager, name, path, px);
}
```

Так же устроены `CreateTextureFromFile`, `CreateMaterial` и дефолт-сеты (`DefaultUpdateSet`/
`DefaultShaderSet` берут `EngineContext*` и достают менеджеры через `ctx->GetXxxManager()`).

## Редактор читает живой ECS — это не баг

Панели ImGui (`UI_Hierarchy`/`UI_Inspector`/…) читают живой ECS и `UI_Yoga` на UI-потоке, пока
sim-поток их мутирует. Худший исход — значение, прочитанное в момент записи (рваная матрица на один
кадр). **Локи сюда не добавлять и это не «чинить».** С `Engine::LoadScene` UI сериализован:
`Engine::scene_swap_mutex` держится весь кадр `RenderFunc`, а UI рисуется внутри него. Гонка есть
только с sim-потоком.

- ECS мутирует только sim-поток. UI-поток читает и шлёт команду (`InputManager::RegisterCommand`/
  `PushCommand`).
- Покадровые правки (драг гизмо) меняют параметры существующих объектов на месте, например запись
  в `Positions`. Destroy+recreate каждый кадр — структурная мутация ECS во время `ForEach` на
  UI-потоке, то есть краш. Пересоздание — только при реальном структурном изменении (так
  `UI_Yoga::Emit`: `Positions` на месте, пересоздание лишь на структурный dirty).

## Архитектура — не догма

Если задача упирается в примитив (нет миграции архетипов, компонент держит указатель вместо имени,
поле не выражается схемой), правильный ответ часто — поменять примитив, а не обходить его в
вызывающем коде. Вместо «нельзя, так устроено» — что именно мешает и во что обойдётся правка.
Граница: менять — да, перестраивать без необходимости — нет. Сначала назвать упирающийся
примитив, потом — минимальную правку именно его.

## Касты — хелперами `Utils.h`

Сужающие и знаковые преобразования в новом коде — через `src/engine/include/Utils.h`, а не
C-кастом или `static_cast`:

| вместо | пиши | проверяет |
|---|---|---|
| `(Uint32)size_t_val` | `safe_u32(v)` | влезает в `Uint32` |
| `(int)uint32_val` | `safe_u32t_i(v)` | влезает в `int` |
| `(uint32_t)int_val` | `safe_i_u32(v)` | неотрицательное |
| `(Sint32)float_val` | `safe_sint32(v)` | конечное и в диапазоне |
| `(Uint32)float_val` | `safe_f_u32(v)` | конечное, ≥ 0, целое, в диапазоне |
| `(float)Sint32_val` | `safe_sint32_f(v)` | ничего, пишется ради единообразия |

Проверки — `assert`: в Release бесплатны, в Debug ловят тихую порчу (отрицательный индекс,
свёрнутый в огромный `Uint32`, обрезанный размер). Расширения без потерь (`int32 → int64`,
`uint8 → uint32`) и уже проверенное строкой выше не заворачивать. Нужного хелпера нет — добавить
его в `Utils.h`.

## SDL и shadercross форкнуты

`external/SDL3` и `external/SDL3_shadercross` — вендоренные копии форков `Nikel12345/SDL` (ветка
`base-3.4.14`) и `Nikel12345/SDL_shadercross` (`main`). Правки помечены `ENGINE-FORK`, комментарии
к ним по-английски. Перед правкой `external/` или разбором поведения SDL — дока форков:
`external/SDL3/docs/README-gpu-queue-families.md`, `README-vulkan-version-requirement.md`,
`README-minimized-window-claim.md` (там же) и `external/SDL3_shadercross/README-fork.md`.
Правка в `external/` уходит тем же коммитом и в форк.

## `debug_name` — только для человека

`debug_name` (`RenderPassStep`, `ComputePassStep`, `BlitPassStep`, `ShaderProgram`,
`ComputeShaderProgram`, `BufferData`, `TextureAtlas`, …) — подпись для логов и редактора. В логике
не участвует: не ключ поиска, не значение для сравнения, не источник имени для сериализации. Его
никто не обязан заполнять, и он может разойтись с ключом реестра — логика на нём становится
скрытой второй системой идентичности.

Ссылка на другой объект хранится **по имени, в собственном поле ссылающегося**
(`ShaderProgram::render_pass_name`, `ComputeShaderProgram::compute_pass_name`, `vs_name`/`fs_name`/
`cs_name`, `BufferDataName`). Указатель резолвят потребители на сборке (PipeManager, BatchBuilder),
получив менеджер параметром:

```cpp
sp->render_pass_name = pass_name;            // а не sp->associated_render_pass = rp
json_write("pass", sp->render_pass_name);    // а не rp->debug_name
RenderPassStep* rp = pass_manager->GetRenderPassStep(sp->render_pass_name);
```

Единственное исключение (избегать): дропдаун выбора прохода в `UI_Inspector` показывает
`debug_name` самих проходов. Понадобилось поле где-то ещё — почти наверняка нужно имя-ссылка.

**Ресурс не хранит свой ключ реестра.** Имя принадлежит реестру. У словаря ключ отдаёт обход
(`for (auto& [name, sp] : GetShaderPrograms())`); нужен порядок — контейнер из ячеек
«имя + объект» (как `ComputeProgramCell`), а не поле `name` в ресурсе. Второй индекс «по имени»
рядом с основным контейнером — второй источник истины, он разойдётся; десятки элементов на холодном
пути ищутся линейно. У вызывающего имя обычно уже есть (он его передал при создании) — не читать
его обратно с объекта.

## Оформление

**Код самодокументируется именами.** Комментарий — только там, где без него не понять: почему
сделано так, а не очевидным способом; грабля, ломающаяся в другом месте; контракт с шейдером или
бэкендом. Пересказ кода, история правки («теперь X вместо Y»), подписи к очевидным блокам — не
писать. При переносе кода чужие комментарии не трогать.

Граница с докой: механика и её «почему» на уровне системы — в доке; комментарий — локальная
ловушка у той строки, где на неё наступят. Что уже описано в доке, комментарием не повторять.
Ловушку записывать как проблему (что сломается и как), без рассуждения, почему сейчас она не
стреляет.

**Доки (`docs/`) — тем же стилем, что уже есть**, по-русски: проза абзацами о том, как устроено
сейчас и почему (не история изменений и не план), таблица для перечислимого (уровни, поля), главный
инвариант жирным, в конце раздел «Инварианты и грабли», ссылки на соседние доки. Правка механики
переписывает затронутые места доки на новое состояние, а не дописывает «раньше было».

## `WARNINGS.md`

Механики, которые ломаются не там и не тогда, где сделана ошибка (поздний usage-флаг, порядок
compute-программ, …). Читать при правке жизненного цикла GPU-ресурсов и порядка проходов; новый
случай — дописать разделом.

Остальные проектные заметки — в авто-памяти (индекс `MEMORY.md`).
