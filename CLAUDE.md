# ЧИТАТЬ ПЕРЕД НАЧАЛОМ РАБОТЫ

Этот файл автоматически загружается Claude Code в каждой сессии. Здесь — стойкие
архитектурные правила проекта, которые нельзя нарушать.

## ⚠️ Менеджеры НЕ владеют друг другом

Менеджеры движка (`TextureManager`, `ModelManager`, `MaterialManager`, `ShaderManager`,
`BufferManager`, `CameraManager`, `FontManager`, `PassManager`, `PipeManager`, …)
**не держат указателей друг на друга и не вызывают друг друга напрямую**. Каждый владеет
только своим состоянием.

**Почему:** менеджеры обязаны оставаться листовыми/развязанными — это держит слоёную
CMake-структуру (`EngineEcs` / `EngineGpu` / `Engine`) и позволяет модулю физики линковать
лишь часть из них. Менеджер, владеющий менеджером, = циклы и протечка зависимостей.

**Как правильно:** кроссменеджерские операции живут на **`EngineContext`** — он держит все
менеджеры. Публичный метод объявляется на `EngineContext`, а он передаёт нужные менеджеры
**параметрами** в листовой метод, который их НЕ хранит.

```cpp
// EngineContext.cpp
FontHandle* EngineContext::CreateFont(const std::string& name, const char* path, int px) {
    return font_manager->CreateFont(texture_manager, buffer_manager, name, path, px);
    //                              ^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^  чужие менеджеры — аргументами
}
```

Тот же паттерн уже есть: `EngineContext::CreateTextureFromFile`, `CreateMaterial`,
дефолт-сеты (`DefaultUpdateSet`/`DefaultShaderSet` берут `EngineContext*` и достают
менеджеры через `ctx->GetXxxManager()`).

## Редактор читает ЖИВОЙ ECS — это НЕ баг

Панели редактора (ImGui: `UI_Hierarchy`/`UI_Inspector`/…) **читают живой ECS/UI_Yoga прямо на UI-потоке**,
пока sim-поток может их мутировать. Это **осознанный компромисс**, а не гонка, которую надо «чинить»:
худшее — прочитать значение в момент записи (рваная матрица на один кадр), что для редактора безвредно.
**НЕ добавляй сюда локи/мьютексы и не «исправляй» это.**

Что при этом ЗАМКНУТО (не путай): `Engine::scene_swap_mutex` держится **весь кадр** в `RenderFunc`,
а UI рисуется внутри него (`UI_ImGui::Iterate`). Значит UI полностью сериализован с `Engine::LoadScene`
(снос+пересборка ECS, дерева UI и словарей менеджеров). Незамкнут только **sim-поток** — с ним одним
и есть гонка.

Правила, которые из этого следуют:
- **Мутирует ECS только sim-поток** — через команды `InputManager` (`RegisterCommand`/`PushCommand`),
  а не UI-поток напрямую. UI-поток читает и **шлёт команду**.
- **Для покадровых правок** (драг гизмо и т.п.) **мутируй ПАРАМЕТРЫ существующих объектов на месте**
  (напр. запись в `Positions`), а НЕ destroy+recreate. Пересоздание сущностей **каждый кадр** гонит
  структурную мутацию ECS во время `ForEach` на UI-потоке → **краш**. Recreate допустим лишь при
  реальном структурном изменении (добавили/убрали объект), редко. (Так лечился краш драга UI-узла:
  `UI_Yoga::Emit` обновляет `Positions` энтити на месте, recreate — только на структурный dirty.)

## Архитектура — не догма: мы тут пишем движок

Текущий код — **не рамка, в которую надо втискивать решение**. Если задача упирается в
существующий примитив (нет миграции архетипов, компонент держит указатель вместо имени,
поле не выражается схемой) — правильный ответ часто **«поменять примитив»**, а не городить
обход в вызывающем коде. Предлагай правку ядра, если она локальная и снимает класс проблем.
Не отвечай «нельзя, потому что сейчас так устроено» — отвечай, ЧТО именно мешает и во что
обойдётся это изменить.

Граница: **менять — да, перестраивать без необходимости — нет.** Не переписывай подсистему
целиком ради одной фичи и не трогай работающее, если изменение не окупается. Сначала назови
упирающийся примитив, потом — минимальную правку именно его.

## Приведение типов — хелперами `Utils.h`, а не C-кастами

В `src/engine/include/Utils.h` лежат проверяемые преобразования. В новом коде **сужающие и
знаковые** касты пишутся ими, а не `(Uint32)x` / `static_cast`:

| вместо | пиши | что проверяет |
|---|---|---|
| `(Uint32)size_t_val` | `safe_u32(v)` | влезает в `Uint32` |
| `(int)uint32_val` | `safe_u32t_i(v)` | влезает в `int` |
| `(uint32_t)int_val` | `safe_i_u32(v)` | не отрицательное |
| `(Sint32)float_val` | `safe_sint32(v)` | конечное и в диапазоне |
| `(Uint32)float_val` | `safe_f_u32(v)` | конечное, ≥ 0, целое, в диапазоне |
| `(float)Sint32_val` | `safe_sint32_f(v)` | расширение — проверять нечего, но пишем единообразно |

**Почему:** проверки — `assert`, в Release их нет, то есть цена нулевая. Зато в Debug ловится
ровно тот класс ошибок, который иначе всплывает не исключением, а тихой порчей: отрицательный
индекс, свёрнутый в гигантский `Uint32`, размер, обрезанный на переполнении, координата,
уехавшая на пиксель. C-каст такое молча пропускает.

```cpp
// было: молча свернёт cell == -1 в 4294967295
bi.destination.x = (Uint32)(s.cell % (int32_t)PER_ROW) * CELL;
// стало: assert поймает отрицательную ячейку там, где она появилась
t.dx = safe_i_u32(s.cell % safe_u32t_i(PER_ROW)) * CELL;
```

**Границы:** расширяющие преобразования без потери (`int32 → int64`, `uint8 → uint32`) хелпера
не требуют. Не заворачивай и то, что уже гарантировано типом или проверено строкой выше —
хелпер должен стоять там, где допущение реально есть. Нужного преобразования нет в `Utils.h` —
добавь его туда, а не пиши каст на месте.

## `debug_name` — только для человека, никогда для логики

Поле `debug_name` (у `RenderPassStep`, `ComputePassStep`, `BlitPassStep`, `ShaderProgram`,
`ComputeShaderProgram`, `BufferData`, `TextureAtlas`, …) существует **исключительно для логов и
редактора**. В логике оно не участвует: ни как ключ поиска, ни как значение для сравнения, ни как
источник имени для сериализации.

Само по себе поле законно и полезно: коду, которому досталась голая ссылка на ресурс, надо чем-то
назвать его в сообщении об ошибке (`PipeManager` получает `ShaderProgram*` без доступа к реестру).
Законно оно ровно до тех пор, пока ключ реестра лежит в реестре, а не здесь, — см. вторую половину
правила ниже.

**Почему.** Это поле — удобство, а не контракт: его никто не обязан заполнять, и оно может
разойтись с настоящим ключом реестра. Как только на него завязывается логика, оно превращается
в скрытую вторую систему идентичности — и правка «для читаемости лога» тихо ломает загрузку сцены
или резолв ресурса. Обратный ход «указатель → имя через `debug_name`» особенно коварен: он
работает, поэтому его не замечают, и объект начинает хранить указатель там, где обязан хранить имя.

**Как правильно.** Ссылку на другой объект держат **по имени**, и это имя — собственное поле
ссылающегося: `ShaderProgram::render_pass_name`, `ComputeShaderProgram::compute_pass_name`,
`vs_name`/`fs_name`/`cs_name`, `BufferDataName` в списках буферов. Резолв в указатель делают
потребители на сборке (PipeManager, BatchBuilder), получая нужный менеджер **параметром**.
Тогда имя переживает сериализацию, а `debug_name` остаётся тем, чем должен быть, — подписью.

```cpp
// НЕТ: имя восстановлено из чужого debug_name, объект держит указатель
sp->associated_render_pass = rp;
json_write("pass", sp->associated_render_pass->debug_name);

// ДА: имя — своё поле; указатель добывается на месте использования
sp->render_pass_name = pass_name;
json_write("pass", sp->render_pass_name);
RenderPassStep* rp = pass_manager->GetRenderPassStep(sp->render_pass_name);
```

**Исключение — UI**, и его лучше избегать. Сейчас `debug_name` читает только дропдаун выбора
прохода в `UI_Inspector`: там перечисляются сами проходы, и подпись — это и есть то, что нужно
показать. Если поле понадобилось где-то ещё, кроме отрисовки списка, — почти наверняка нужно
не оно, а нормальное имя-ссылка.

### Обратная сторона того же правила: ресурс не хранит собственный ключ

Обращение к `debug_name` — обычно лишь **симптом**. Настоящая болезнь — обратная связь
«ресурс → ключ»: объект знает, под каким именем он лежит в реестре. Переименовать поле в `name`
её не лечит, только маскирует.

Владелец имени — **реестр**, а не то, что в нём лежит. Если реестр словарь, ключ отдаёт обход
(`for (auto& [name, sp] : GetShaderPrograms())`), и поля в объекте не нужно. Если реестру нужен
порядок и словарь не годится — контейнер делают из **ячеек**, а не заводят поле в ресурсе:

```cpp
// НЕТ: программа помнит, как её зовут в реестре
struct ComputeShaderProgram { std::string name; /*…*/ };
std::vector<std::unique_ptr<ComputeShaderProgram>> programs;

// ДА: имя принадлежит ячейке реестра, обход отдаёт пару — как у словаря
struct ComputeProgramSlot { std::string name; std::unique_ptr<ComputeShaderProgram> program; };
std::vector<ComputeProgramSlot> programs;
```

Тот же признак — второй индекс «по имени» рядом с основным контейнером: это ещё один источник
истины про то же самое, и он обязательно разойдётся. Десятки элементов на холодном пути ищутся
линейно и бесплатно.

И у вызывающего имя, как правило, **уже есть** — он сам его и передал при создании. Читать его
обратно с объекта (`csp->name`) незачем: подставь то же выражение, а если оно вычисляется в
цикле — заведи локальную переменную и отдай её в оба вызова.

## Грабли, которые не сигналят о себе — `WARNINGS.md`

В корне репо лежит `WARNINGS.md`: механики, которые ломаются НЕ там и НЕ тогда, где сделана
ошибка (поздний usage-флаг, значимый порядок compute-программ, …). Заглядывай туда, когда правишь
жизненный цикл GPU-ресурсов или порядок проходов, и дописывай новые случаи разделом по теме.
