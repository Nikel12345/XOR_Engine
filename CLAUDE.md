# ЧИТАТЬ ПЕРЕД НАЧАЛОМ РАБОТЫ

Этот файл автоматически загружается Claude Code в каждой сессии. Здесь — стойкие
архитектурные правила проекта, которые нельзя нарушать.

## ⚠️ Менеджеры НЕ владеют друг другом

Менеджеры движка (`TextureManager`, `ModelManager`, `MaterialManager`, `ShaderManager`,
`BufferManager`, `CameraManager`, `FontManager`, `PassManager`, `PipeManager`, …)
**не держат указателей друг на друга и не вызывают друг друга напрямую**. Каждый владеет
только своим состоянием.

**Почему:** менеджеры обязаны оставаться листовыми/развязанными — это держит слоёную
CMake-структуру (`EngineEcs` / `EngineGpu` / `Engine`) и позволяет модулю физики линковать
лишь часть из них. Менеджер, владеющий менеджером, = циклы и протечка зависимостей.

**Как правильно:** кроссменеджерские операции живут на **`EngineContext`** — он держит все
менеджеры. Публичный метод объявляется на `EngineContext`, а он передаёт нужные менеджеры
**параметрами** в листовой метод, который их НЕ хранит.

```cpp
// EngineContext.cpp
FontHandle* EngineContext::CreateFont(const std::string& name, const char* path, int px) {
    return font_manager->CreateFont(texture_manager, buffer_manager, name, path, px);
    //                              ^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^  чужие менеджеры — аргументами
}
```

Тот же паттерн уже есть: `EngineContext::CreateTextureFromFile`, `CreateMaterial`,
дефолт-сеты (`DefaultUpdateSet`/`DefaultShaderSet` берут `EngineContext*` и достают
менеджеры через `ctx->GetXxxManager()`).

## Редактор читает ЖИВОЙ ECS — это НЕ баг

Панели редактора (ImGui: `UI_Hierarchy`/`UI_Inspector`/…) **читают живой ECS/UI_Yoga прямо на UI-потоке**,
пока sim-поток может их мутировать. Это **осознанный компромисс**, а не гонка, которую надо «чинить»:
худшее — прочитать значение в момент записи (рваная матрица на один кадр), что для редактора безвредно.
**НЕ добавляй сюда локи/мьютексы и не «исправляй» это.**

Правила, которые из этого следуют:
- **Мутирует ECS только sim-поток** — через команды `InputManager` (`RegisterCommand`/`PushCommand`),
  а не UI-поток напрямую. UI-поток читает и **шлёт команду**.
- **Для покадровых правок** (драг гизмо и т.п.) **мутируй ПАРАМЕТРЫ существующих объектов на месте**
  (напр. запись в `Positions`), а НЕ destroy+recreate. Пересоздание сущностей **каждый кадр** гонит
  структурную мутацию ECS во время `ForEach` на UI-потоке → **краш**. Recreate допустим лишь при
  реальном структурном изменении (добавили/убрали объект), редко. (Так лечился краш драга UI-узла:
  `UI_Yoga::Emit` обновляет `Positions` энтити на месте, recreate — только на структурный dirty.)
