# Переключаемые варианты текстур — план

Слот материала (например `Albedo`) держит **несколько** текстур; рисуется одна. Выбор —
**per-object** состояние, не per-material: два куба с одним материалом показывают разные
варианты и остаются в одном инстанс-батче.

Статус: часть 1 (слой данных) расписана, часть 2 (GPU) — конспектом.
Сверено с деревом батчей после `3e47d7b` (params → `SpBinding`, ключ батча по ресурсам sp).

## Терминология

Четыре уровня, которые легко перепутать:

| термин | что это | где живёт | гранулярность |
|---|---|---|---|
| **блок** | `UVL_Block` — где текстура лежит в атласе (uv offset/scale/layer) | пуш `uvl_push` | одна текстура |
| **элемент** | все состояния одной сущности | буфер `TextureState` | сущность |
| **секция** | часть элемента под один материал сущности; ровно `MAX_VARIATIVE_SLOTS` ячеек | буфер `TextureState` | (сущность, материал) |
| **ячейка** | один `uint` = номер выбранного варианта | секция | (сущность, материал, вариативный слот) |

Отдельно — два слова, которые смешать легче всего, потому что оба про «варианты»:

- **вариант** — одна из текстур слота (`Material::textures[role][i]`). Свойство **материала**;
  слот с >1 вариантом называется **вариативным**.
- **состояние** — какой из вариантов выбран (`MaterialRef::states` в ECS, ячейка в буфере).
  Свойство **сущности**.

Поэтому «у сущности нет состояний» и «у материала нет вариантов» — разные условия, и гейт
элемента стоит на первом (см. 4b).

```
ПУШ (uniform, собирается на пару ШЕЙДЕР + МАТЕРИАЛ — это и есть texture-батч)
  uvl_push[]      UVL_Block  -- где в атласе лежит каждая текстура, включая варианты
  slot_layout[]   uint       -- (base<<16)|(cell<<8)|count на слот шейдера
  material_index  uint       -- каким по счёту идёт этот материал у сущности

БУФЕР InstanceData (storage, строка на объект)
  .state_offset   int        -- где в TextureState начинается элемент сущности; -1 = нет

БУФЕР TextureState (storage, один на всю сцену, ПЛОСКИЙ) -- НОМЕРА вариантов, ничего больше
  [ ... элемент энтити A ... | ... элемент энтити B ... ]
                                    |
                                    +- секция материала 0 : MAX_VARIATIVE_SLOTS ячеек
                                    +- секция материала 1 : MAX_VARIATIVE_SLOTS ячеек
```

Номер из ячейки уходит индексом в пуш: `uvl_push[base + номер]` — вот там уже настоящий UVL.

Одно и то же состояние живёт в трёх представлениях, каждое уместно на своём месте:

| где | чем адресуется | почему так |
|---|---|---|
| ECS (`MaterialRef.states`) | по **роли**, разреженно | переживает правку набора ролей и вариантов материала |
| буфер `TextureState` | по **ячейке** | фиксированный страйд секции → смещение умножением |
| пуш `slot_layout` | **перевод** слот шейдера → ячейка | считается на пару (шейдер, материал) |

## Принятые решения и почему

Раздел существует, чтобы не переигрывать заново уже закрытые развилки.

**Состояние — per-instance канал, не пуш.** Пуш uniform-а работает на texture-батч, а батч
= один `SDL_DrawGPUIndexedPrimitivesIndirect` на тысячи инстансов. Per-object данные ходят
только через буфер, индексируемый строкой (`row`), как `Transforms`/`InstanceData`.
Вариант «состояние в ключ батча» отброшен: взрыв дерева + структурная пересборка на каждое
переключение.

**ВСЁ, ЧТО УХОДИТ В ПУШ, ОБЯЗАНО ВХОДИТЬ В КЛЮЧ TEXTURE-БАТЧА.** После `3e47d7b` ключ — это
ресурсы, которые потребляет именно эта sp (хэндлы текстур её `required_slots` + адрес блоба
`SpBinding::params`), а НЕ идентичность материала. Значит два РАЗНЫХ материала попадают в один
узел, если дают этой sp одинаковые текстуры и у обоих нет params (ShadowCaster, Wireframe и
любая sp с текстурами, но без `MaterialBlock` — напр. depth-prepass с alpha-test). Всё, что
план добавляет в пуш, обязано попасть в ключ, иначе схлопнувшиеся материалы получат чужой пуш:
все варианты каждого слота (не только дефолт), `cell`, `material_index`.

**Уточнение правила: «в пуше» значит «шейдер это ЧИТАЕТ».** Поле, которое запушено, но при
данной раскладке гарантированно не читается, в ключ не вносится — иначе ключ дробит узлы за
данные, ни на что не влияющие. Единственный такой случай — `material_index` у НЕВАРИАТИВНОГО
узла (все `count == 1`): гард `count > 1` не пускает обращение к `TextureState` ни на одном
слоте, значит `section_ofs` не вычисляется вовсе. См. развилку про `MatSpLayout::variative`
ниже — без неё правило в буквальном прочтении стоило теневому проходу 6 draw'ов вместо одного.

**Раскладка таблицы UVL — сгруппированная по слотам,** дефолт = вариант 0 внутри группы.
Отдельная «плотная голова» из дефолтов рассматривалась и отброшена: групповая раскладка даёт
`idx = base + v` без `-1`, без константы N и без ветки на `v == 0`, а у материала без
вариантов вырождается в сегодняшнюю таблицу (`count` все единицы → `base[s] == s`).
Взамен — контракт: индекс блока слота НЕ равен `s`, любой пролог обязан идти через `base`.

**Секция — ФИКСИРОВАННЫЕ `MAX_VARIATIVE_SLOTS` ячеек, смещение = `material_index *
MAX_VARIATIVE_SLOTS`, `material_index` в ключ батча.** Рассматривался и отброшен `slot_prefix`
(сумма ролей предыдущих материалов сущности): он принимает столько значений, сколько бывает
уникальных сумм, то есть дробит батчи непредсказуемо и невидимо. `material_index` принимает
0, 1, 2 — рост ограничен максимальным числом сабмешей и очевиден глазами. Память при этом
ничтожна: платят только сущности с вариантами.

**`material_index` идёт в ключ ТОЛЬКО у вариативного узла** (`MatSpLayout::variative` — есть хоть
один слот с `count > 1`); у остальных он ноль и в ключ не вносится. Без этого гейта дробление
платят и те узлы, которые состояние не читают, — а это как раз самые схлопнутые узлы в движке.
ЗАМЕРЕНО счётчиком в `FinalizeOffsets` (`[batch] pass ...: draws=/cmds=`) на сцене `game`:

| проход | база | `material_index` безусловно | с гейтом `variative` |
|---|---|---|---|
| shadow | 1 | **6** | 1 |
| main | 11 | 12 | 11 |
| transparent | 1 | 2 | 1 |

Худший случай — тень: `ShadowCaster` не берёт у материала ничего, все материалы дают ей ОДИН
узел и один draw на 10 команд, и номер сабмеша разносил его на шесть. С гейтом дерево сцены без
вариантов совпадает с базой байт-в-байт — то самое вырождение в сегодняшнее поведение, которое
обещает раскладка UVL.

Отброшены также: заголовок со смещениями секций в начале элемента (лишнее зависимое чтение
буфера) и доставка номера материала через каллинг (`CmdMaterialIndex` + параллельный компактный
выход скаттера — трогает `culling_pib.comp` и сентинел `-1` в `out_pib`).

**`cell` пушится, а не выводится шейдером.** `cell` — порядковый номер роли среди
**вариативных** ролей материала (`count > 1`), в порядке enum. Шейдер его вычислить не может:
он не знает ни набор ролей материала, ни какие из них вариативны.

Отдельно рассматривался и ОТБРОШЕН вариант «`cell` = канонический номер роли»
(`Albedo=0, Normal=1, ORM=2, Emissive=3`), при котором `cell` не нужно ни пушить, ни ключевать.
Он привязывает размер секции к ГЛОБАЛЬНОМУ пространству ролей, а не к числу вариативных слотов:
шейдеру на `Custom1..Custom4` достались бы номера 5..8, и при страйде 4 он остался бы без
вариантов вовсе, хотя слотов у него ровно четыре. `MAX_VARIATIVE_SLOTS` меряет «сколько слотов
может нести варианты» и одинаково работает для PBR и Custom.

Пушный `cell` попутно закрывает два сценария, на которых сломалась бы любая выводимая
нумерация:
- **leftover-роли.** `RemoveMaterialShader` (`DefaultCommandSet.cpp:236`) намеренно не чистит
  роли удалённого sp: «leftover-роли в textures не чистим — безвредны». Сегодня безвредны,
  потому что таблица UVL строится обходом `sp->required_slots`;
- **несколько sp у материала.** `AddMaterialShader` (`:227`) добирает роли нового sp, то есть
  набор ролей материала = ОБЪЕДИНЕНИЕ по всем его sp и не равен списку ни одного из них.

**`MAX_VARIATIVE_SLOTS` уезжает в шейдер через `ShaderDefine`,** а не дублируется литералом.
Механизм появился в движке (`ShaderTypes.h::ShaderDefine`, хвостовой параметр `Create*Shader`):
шейдер объявляет константу через `#ifndef/#define`, вызов её переопределяет. Дефайны входят в
ключ кэша `.spv` (`ShaderManager::LoadOrCompileSPIRV`), поэтому смена константы сама
инвалидирует кэш — молча разъехаться CPU и байткоду нельзя.

**Компонент хранит состояния ПО РОЛИ, а не по номеру ячейки.** Номер ячейки сдвигается, когда
у материала меняется набор вариативных ролей; роль — нет.

**Сентинел «нет вариантов» = `-1`.** Буфер объявляется `StructuredBuffer<int>`, проверка `< 0`
— как `PIB_DataModule::kNoRow`. НЕ `uint` с `< 0`: это всегда false, молча.
Альтернатива «зарезервированный нулевой элемент + `prefix = 0`» убирает одну когерентную
ветку и читается хуже — отброшена.

**Гард `count > 1` и кламп `v >= count → 0` в шейдере обязательны.**
Гард: слот с одним вариантом состояние читать не должен — и потому что читать нечего, и потому
что у слота, которого у материала нет (подставлен dummy), ячейки не существует.
Кламп: таблица плотная, и при удалении варианта `count`/таблица пересчитываются, а номер в
компоненте — нет; `base + v` уехал бы в блоки СЛЕДУЮЩЕГО слота (нормалка сэмплится как альбедо
— правдоподобная неправильная картинка без строки в логе). Одно сравнение покрывает это, смену
материала, правку `materials.json` руками и любой транзиентный кадр. CPU-подрезка при удалении
варианта не нужна: дороже и не полная.

**Префиксная сумма пересчитывается каждый кадр.** Гейт по dirty от правок материала/состояний —
отложен (см. «Отложено»).

## Итоговая схема данных

```
МАТЕРИАЛЫ
  wood    Albedo = [alb_d, alb_1, alb_2]   Normal = [norm_d, norm_1]   ORM = [orm]
  metal   Albedo = [m_alb]

  вариативные роли wood: Albedo (cell 0), Normal (cell 1)   -- ORM не вариативна, ячейки нет
  вариативные роли metal: нет

СУЩНОСТЬ "стул"  materials = [ wood, metal ]      (порядок = submesh.material_index)
  элемент = 2 секции по MAX_VARIATIVE_SLOTS(=4) = 8 ячеек
  InstanceData[row].state_offset = 16
  TextureState[16..19] = [2, 0, _, _]   секция wood:  albedo -> вариант 2, normal -> дефолт
  TextureState[20..23] = [_, _, _, _]   секция metal: вариантов нет

TEXTURE-БАТЧ (шейдер Lit + материал wood, material_index = 0)
  uvl_push    = [alb_d, alb_1, alb_2, norm_d, norm_1, orm]
  slot_layout = [ (base=0,cell=0,count=3), (base=3,cell=1,count=2), (base=5,cell=0,count=1) ]
  material_index = 0                                             ^^^^^^ cell не используется
```

Адресация в пиксельном шейдере для слота `s`:

```
g_stateOfs   = InstanceData[row].state_offset             // -1 = вариантов нет (из VS)
section_ofs  = material_index * MAX_VARIATIVE_SLOTS       // из пуша, дефайн общий с CPU
L            = slot_layout[s]
count        = L & 0xFF
v            = (count > 1 && g_stateOfs >= 0)
               ? TextureState[g_stateOfs + section_ofs + ((L >> 8) & 0xFF)]
               : 0
v            = (v >= count) ? 0 : v                       // кламп протухшего
uvl          = uvl_push[(L >> 16) + v]
```

**Ключевые свойства.** Материал без вариантов → `count == 1` везде, `base[s] == s`, таблица
байт-в-байт сегодняшняя, у всех сущностей `state_offset == -1`, буфер состояний не читается:
нулевая регрессия. Смена варианта — запись в компонент, дерево батчей не трогается.
Смена НАБОРА вариантов — структурная, требует `SetDirtyBatches`.

# ЧАСТЬ 1 — слой данных

После этой части буферы заполнены правильными данными, но шейдер их не читает: поведение
движка не меняется ни на пиксель.

## Блок 1. `Material`: слот-роль → вектор имён

**`MaterialData.h`**

```cpp
struct Material {
    // Слот держит СПИСОК текстур: [0] — то, что рисуется по умолчанию, дальше варианты,
    // переключаемые состоянием на сущности. Пустой вектор = слота у материала нет.
    // Слот с >1 текстурой называется ВАРИАТИВНЫМ и получает ячейку в секции состояний.
    // std::map, а не unordered_map: порядок ролей задаёт нумерацию ячеек (cell), и он обязан
    // быть детерминированным — его независимо считают BatchBuilder и модуль заливки.
    std::map<TextureSlotRole, std::vector<TextureName>> textures;
    ...
};
```

`shader_programs` (`vector<SpBinding>`), `retired_params` и `FindBinding` не трогаются.

**`MaterialManager::CreateMaterial`** — тип параметра `vector<pair<role, vector<TextureName>>>`.

**`MaterialManager::CollectSamplerUsage`** — обходит ВСЕ элементы вектора. Пропустишь — атлас
редкого варианта не получит `SDL_GPU_TEXTUREUSAGE_SAMPLER`, и сломается не здесь, а на первом
кадре, где этот вариант включили (`WARNINGS.md`, поздний usage-флаг).

**`EngineContext::CreateMaterial`** (`EngineContext.h:68`) — тип в `initializer_list`;
к существующей валидации `required_slots` добавляется проверка **«все варианты одного слота
лежат в одном атласе»** (варнинг, не отказ). Причина: на слот биндится один `Texture2DArray`,
UVL адресует слой внутри него — вариант из чужого атласа переключить нечем.

**Сериализация** — `Engine_Scene.cpp` (save/load материалов) и `MaterialEntry`:

```json
"textures": [ { "role": "Albedo", "textures": ["wood_d", "wood_cracked"] } ]
```

Чтение старого формата (`"texture": "имя"` скаляром) даёт вектор из одного элемента —
существующие сцены не переписываются.

## Блок 2. `MaterialComponent`: имя + состояния

**`BaseComponents.h`**

```cpp
// Ссылка сущности на материал + её собственное состояние вариантов. Имя — как было
// (name-based ссылка, резолв на сборке батча). Ячейка, а не две параллельные коллекции, —
// тот же приём, что SpBinding в MaterialData.h: у списка и данных один владелец.
// states РАЗРЕЖЕННЫЕ и ПО РОЛИ, а не по номеру ячейки: номер зависит от набора вариативных
// ролей материала и сдвигается при его правке, роль — нет. Пусто = все слоты дефолтные.
// Состояние здесь, а не в материале: это per-object величина, материал у объектов общий.
struct MaterialRef {
    std::string                                       name;
    std::vector<std::pair<TextureSlotRole, uint32_t>> states;    // роль -> номер варианта
};

// Порядок = submesh.material_index, как раньше был порядок names.
struct MaterialComponent {
    std::vector<MaterialRef> materials;
};
```

Имя `MaterialData` занято (`MaterialData.h` → `struct Material`), поэтому `MaterialRef`.

**`ComponentSerializer.cpp:224`–`291`** — там уже ручные save/load под `names` (`FieldSpec`
умеет только скаляры), правятся на пары имя+вектор пар. Пустой `states` в файл не пишется.

## Блок 3. `BatchBuilder`: раскладка, ключ, таблица UVL

### 3a. Предпроход `BuildMaterialLayouts`

`AddEntityToBatches` прогоняет цикл по `required_slots` **четыре раза на каждую сущность**, и
все четыре — чистые функции пары (материал, sp), от сущности не зависящие ничем:

| что | сейчас | после |
|---|---|---|
| `HashAtlasBatchKey` | резолв хэндла на слот | `MatSpLayout::atlas_key` |
| `AtlasBatchData::texture_binding` | резолв хэндла + dummy-фолбэк на слот | готовый вектор |
| `HashTextureBatchKey` | резолв хэндла на слот | `MatSpLayout::res_key` |
| `TextureBatchData::texture_uvl` | резолв хэндла на слот | готовый вектор |

С вариантами каждый из них умножился бы на среднее число вариантов. Предпроход не добавляет
расход, а **снимает** уже существующие поиски по строке: варианты платятся один раз на
материал, а не на объект.

```cpp
// BatchKeys — рядом с ShaderBatchKey/AtlasBatchKey/TextureBatchKey
using MatSpKey = uint64_t;   // (Material*, ShaderProgram*)

// RenderCommandData.h — рядом с TextureBatchData/AtlasBatchData: это буквально их
// пер-материальная половина, всё, что не зависит от сущности.
struct MatSpLayout {
    std::vector<UVL_Block>                    uvl;              // таблица целиком, порядок required_slots
    std::vector<SDL_GPUTextureSamplerBinding> texture_binding;  // бинды атласов слотов
    uint32_t       slot[MAX_SLOTS];                             // (base<<16)|(cell<<8)|count
    MatSpKey       res_key;                                     // ресурсный вклад в ключ texture-батча
    AtlasBatchKey  atlas_key;                                   // от сущности не зависит вовсе
    bool           bindable;                                    // и dummy нет → sp пропускается
    bool           variative;                                   // есть слот с count > 1 → узел читает состояние
};
```

```cpp
// BatchBuilder.h, private
// Пер-материальная половина батча. Считается предпроходом в начале UpdateRenderBatches и
// живёт до конца этого вызова — между вызовами НЕ валидна (та же дисциплина, что у
// PIB_DataModule::row_of).
// Инвалидации по событиям нет НАМЕРЕННО: протухнуть таблица может от правки списка вариантов,
// переименования/удаления текстуры, правки sp у материала и репака атласа (UVL живых текстур
// едут — см. инвариант в TextureBatchData). Точка инвалидации в движке одна — пересборка
// дерева; вторая система инвалидации рядом с ней обязательно разойдётся.
void BuildMaterialLayouts(MaterialManager* mtm, ShaderManager* sm, TextureManager* tm);
std::unordered_map<MatSpKey, MatSpLayout> mat_sp_layouts;
```

Вызов — в `UpdateRenderBatches` **до** развилки, потому что `AddEntityToBatches` общий для
полной пересборки и инкремента:

```cpp
BuildMaterialLayouts(mtm, sm, tm);
if (dirty_batches.exchange(false)) { BuildRenderBatches(...); FinalizeOffsets(...); ... }
else if (ApplyIncremental(...))    { FinalizeOffsets(...); ... }
```

Предпроход, а не ленивое заполнение: материалов десятки, полный обход дешевле ветки «есть ли в
памятке» в цикле на миллион сущностей. На инкрементальном пути таблица соберётся и умрёт вместе
с вызовом — бесполезно, но и бесплатно.

Он же единственное место, где считается `cell` и где логируется переполнение
`MAX_VARIATIVE_SLOTS`: лог из `AddEntityToBatches` дал бы миллион строк, а тут он естественно
один на материал, без флагов-заглушек.

### 3b. Что считается в раскладке

Один проход по `sp->required_slots`; для каждого слота подряд все его варианты, дефолт первым.
Бегущий счётчик записанных блоков — это `base`:

```
uvl = [ alb_d, alb_1, alb_2, norm_d, norm_1, orm ]
        \_ Albedo _______/  \_ Normal _/  \ORM/
```

| поле | биты | что | как считается |
|---|---|---|---|
| `base` | 16 | индекс первого блока слота в `uvl_push` | бегущий счётчик блоков |
| `cell` | 8 | ячейка секции под состояние слота | сколько ВАРИАТИВНЫХ ролей материала идёт до этой (обход `std::map`) |
| `count` | 8 | сколько у слота вариантов | фактически собранное число блоков |

`count` — ФАКТИЧЕСКИ собранное, а не `material->textures[role].size()`. Вариант с неразрешимым
именем в таблицу не попадает и счётчик уменьшает; иначе базы всех последующих слотов
разъедутся. Дефолт при промахе подменяется dummy и место сохраняет.

Слот с `count == 1` (одна текстура, или слота у материала нет и стоит dummy) ячейку не
занимает; `cell` у него не используется — пишется 0.

**Два гарда переполнения**, оба в предпроходе, оба с одинаковой деградацией — лишним слотам
принудительно `count = 1`, объект показывает дефолт:

- **вариативных ролей больше `MAX_VARIATIVE_SLOTS`** — ячейки в секции кончились;
- **таблица UVL длиннее `MAX_UVL_BLOCKS`** — размер `textures[]` в шейдере это константа
  компиляции, то есть потолок на все материалы сразу.

Поднятие любой из констант становится осознанным решением, а не тихой поломкой.
Флаг-заглушка «уже логировали» не нужен: предпроход идёт по материалам, значит лог и так один
на материал.

### 3c. Ключ texture-батча

Вся логика ключей остаётся свободными функциями наверху TU, где она и живёт. Меняется только
граница разреза — по признаку «зависит от сущности или нет»:

```cpp
// зовёт ПРЕДПРОХОД, один раз на пару (материал, sp)
MatSpKey        HashMatSpResources(const Material* mat, const ShaderProgram* sp,
                                   TextureManager* tm, const std::vector<uint8_t>* params,
                                   const uint32_t* slot_words);
// зовёт AddEntityToBatches — двухстрочный домешив, вызов остаётся однострочным
TextureBatchKey HashTextureBatchKey(MatSpKey res_key, uint32_t material_index);
```

Сегодняшний `HashTextureBatchKey(mat, sp, tm, params)` целиком переезжает в
`HashMatSpResources`: хэндлы текстур `required_slots`, роли, адрес блоба `SpBinding::params` —
всё это функции пары, от сущности не зависит НИЧЕГО. Единственное, что зависит, —
`material_index`.

Что добавляется по правилу «в пуше ⇒ в ключе»:

- хэшировать **все варианты** слота, а не только `it->second`: иначе два материала с одинаковым
  дефолтом, но разными списками вариантов схлопнутся в один узел и получат одну таблицу UVL на
  двоих;
- примешать `cell` слота (он в `slot_words`): наборы вариативных ролей у схлопнувшихся
  материалов могут различаться;
- `material_index` — во второй половине, и ТОЛЬКО при `MatSpLayout::variative`; иначе в
  `HashTextureBatchKey` уходит ноль (см. развилку выше — без этого дробится теневой проход).

**`HashAtlasBatchKey(mat, sp, tm)`** — хэшировать атласы **всех** вариантов слота, а не только
дефолта. Инвариант «все варианты слота в одном атласе» — варнинг, а не отказ; при его нарушении
вариант ≥1 иначе молча сэмплился бы из чужого атласа. Результат тоже уходит в памятку
(`MatSpLayout::atlas_key`) — он от `material_index` не зависит и берётся оттуда как есть.

### 4b. Буфер состояний

- `DEFAULT_TEXTURE_STATE_BUFFER` в `BufferManager.h:24`, создание в `BufferManager.cpp:15`;
- модуль `TextureStateDataModule` (size + store) по образцу `InstanceDataModule`;
- `SetDefaultTextureStateUpdater` в `DefaultUpdateSet`, вызов из `Engine.cpp:461`.

Элемент сущности = `materials.size() * MAX_VARIATIVE_SLOTS` ячеек. Секция материала заполняется
по правилу `cell`: вариативные роли по порядку `std::map`, невариативные пропускаются, хвост
секции нулями.

**Секция есть у КАЖДОГО материала сущности**, включая тот, у которого вариативных ролей нет
вовсе — его секция остаётся нулями и никогда не читается (у всех её слотов `count == 1`, гард
не пускает). Пропустить её нельзя: смещение считается как `material_index *
MAX_VARIATIVE_SLOTS`, и дыра сдвинула бы все последующие секции.

**Элемента НЕТ вовсе**, если ни у одного материала сущности нет непустых `states`.
Гейт считается ПО КОМПОНЕНТУ, а не по материалам: решение принимается без резолва материалов
(дёшево на миллионе строк), и буфер населяют только объекты, у которых что-то реально
переключено. Материал с вариантами, который никто не переключал, в буфер не попадает — типовой
случай: добавили второй альбедо в `brick`, 10 000 стен продолжают показывать дефолт, и ни одна
из них в буфере не существует.

Корректность держат ДВА независимых гарда в шейдере, каждый закрывает свою дыру:

| ситуация | что срабатывает | результат |
|---|---|---|
| у сущности нет переопределений (`states` пуст) | `g_stateOfs >= 0` | буфер не читается, дефолт |
| у слота нет вариантов (или стоит dummy) | `count > 1` | буфер не читается, дефолт |
| материал вариативен, но элемента нет (`-1`) | `g_stateOfs >= 0` | дефолт — как если бы читал нулевую секцию |
| материал вариативен, элемент есть, ячейки нули | — | `v = 0`, дефолт |
| невариативный материал рядом с вариативным | `count > 1` | секция выделена, но мертва |

Ни один из гардов не покрывает случай другого — убирать нельзя ни тот, ни другой.

**Домен обхода — строго `{Positions, DrawComponent}`**, тот же, что у `TransformDataModule`
(`:112`/`:213`/`:236`), `InstanceDataModule` (`:21`/`:33`) и `BoundSphereDataModule` (`:43`),
и тот же, по которому `RecalculateInstanceOffsets` раздаёт `render_instance_base`. Совпадение
обязательное, а не желательное: `state_offset` живёт в `InstanceData`, и разъезд нумерации
строк даст чужие варианты без единого симптома в момент ошибки.

`MaterialComponent` спрашивается **у архетипа**, а не у сущности — по образцу
`PIB_DataModule::BuildRowTable` и `RecalculateInstanceOffsets`, которые обходят
`scene->archetypes` напрямую. Один вопрос на архетип вместо поиска в `unordered_map` на каждую
из миллиона строк (ровно то, от чего уходил `BuildRowTable`). Правка `ForEachArchetype` под
опциональный компонент для этого НЕ нужна.

```cpp
uint32_t running = 0;
for (auto& [sig, arch] : scene->archetypes) {
    if (!arch.get_array<DrawComponent>() || !arch.get_array<Positions>()) continue;
    auto* mats = arch.get_array<MaterialComponent>();   // nullptr = архетип без материалов
    const uint32_t base = arch.render_instance_base;    // авторитетная база строки
    for (i, e : arch.entities) {
        row = base + i;
        mc = mats ? &(*mats)[i] : nullptr;
        если !mc или все states пусты:  instance[row].state_offset = -1; continue;
        instance[row].state_offset = running;
        для каждого m из mc->materials:
            mat  = резолв m.name
            cell = 0
            для каждой роли mat->textures по порядку:
                если у роли <= 1 текстуры: пропустить      // невариативная, ячейки нет
                если cell >= MAX_VARIATIVE_SLOTS: прервать // гард, тот же что в 3b
                state[running + cell] = m.states[роль] либо 0
                ++cell
            running += MAX_VARIATIVE_SLOTS
    }
}
```

`render_instance_base` берётся явно, а не выводится из порядка обхода: полагаться на то, что
`scene->archetypes` и `ForEachArchetype` в `InstanceDataModule` идут одинаково, — лишнее
допущение там, где есть авторитетное поле.

Модулю нужен `MaterialManager`, чтобы резолвить имя и повторить нумерацию `cell`. Он приходит
**параметром** из замыкания update-инструкции (как `om`/`bm` сейчас), полем НЕ хранится — см.
CLAUDE.md.

**Transformless-дровабл вариантов не получает.** Домен батча ШИРЕ домена строки:
`BuildRenderBatches` идёт `ForEach<DrawComponent>` без `Positions` (скайбокс батчится, но строки
трансформа не имеет — `StorePIB` пишет ему `-1`). Состояние адресуется через
`InstanceData[row]`, значит у такой сущности его физически негде взять. Это то же ограничение,
что у per-instance `alpha`/`flags` сегодня, и оно осознанное — скайбоксу варианты не нужны.

### 4c. Инвариант, который надо закомментировать

Нумерацию `cell` независимо считают ДВА места: `BatchBuilder::BuildMaterialLayouts` (для пуша,
блоки 3a–3b) и `TextureStateDataModule` (для записи секции, 4b). Плюс `InstanceDataModule`
независимо считает бегущий `state_offset`. Расходиться им нельзя.

Модули — РАЗНЫЕ update-инструкции (`CreateUpdateInstruction` заводится на имя буфера, одна
инструкция два буфера не пишет). Согласованы они только потому, что обе — детерминированные
функции одного и того же ECS + одних и тех же материалов, а те между ними не мутируют: обе идут
на sim-потоке в одной фазе prepare. Пуш согласован потому, что дерево пересобрано до заливки.

Вынос любого из трёх в другой поток или под отдельный dirty-гейт даст разъехавшиеся смещения —
без краша, без лога, просто чужие варианты у части объектов. Комментарий во всех трёх местах +
раздел в `WARNINGS.md`.

Практический вывод, который надо повторить дословно в обоих местах: **вариативная роль —
это роль с >1 текстурой; порядок — обход `Material::textures` (`std::map`); неразрешимое имя
материала = 0 вариативных ролей; переполнение `MAX_VARIATIVE_SLOTS` обрывает нумерацию.**

# ЧАСТЬ 2 — GPU (конспект, детализировать)

**Блок 5. Пуш в `ExecuteRenderBatches`** (`RenderManager.cpp:~428`). Третий fragment-uniform
ПОСЛЕ params, чтобы не двигать `MATERIAL_BLOCK_REGISTER`: `b0` uvl, `b1` params,
`b2` variant layout.

`material_index` едет ВНУТРИ этого же cbuffer-а, а не отдельным пушем: он часть той же
пер-батчевой раскладки, присутствует ровно тогда же, когда она, и не занимает лишний слот.
Хвостовым скаляром — упаковка тут однозначна: `slot_layout` занимает `MAX_SLOTS/4` регистров
(48 байт при 12 слотах), то есть массив кончается НА 16-байтной границе, и следующее поле
ложится ровно на неё:

```hlsl
cbuffer VariantLayoutBlock : register(b2, space3) {
    uint4 slot_layout[MAX_SLOTS / 4];   // (base<<16)|(cell<<8)|count на слот
    uint  material_index;               // offset 48 — начало нового регистра
};
```

Зеркальная структура на CPU — `VariantLayout` из блока 3d, поля в том же порядке.

Никакой новой логики слотов не требуется — работает существующий контракт: пользовательский
пуш занимает слоты 0..N-1 сам (`PushConstantBinder::frag_count` инкрементится в
`PushFragment`), движковые идут следом в ФИКСИРОВАННОМ порядке. Отсутствующий элемент не
занимает слот с обеих сторон сразу: на CPU у него нет данных (`texture_uvl.empty()`,
`params == nullptr`), а в шейдере неиспользуемое объявление вырезает DXC, и рефлексия его не
покажет. Гейт по `frag_uniform_count` остаётся тот же, что у params.

**Блок 6. Регистрация `TextureState` у sp.** Имя в КОНЕЦ `fragment_shader_buffer_names` тех sp,
которым нужны варианты (`Engine::InitDefaultShaders`). Shadow/depth-sp не получают.

Это BINDING, а не пуш, поэтому гейт «нет данных на CPU» его не покрывает: список имён
резолвится в `BatchBuilder` и биндится целиком с индекса 0. Безопасно оно ровно из-за
ХВОСТОВОЙ позиции: если DXC вырежет неиспользуемый `TextureState`, счёт из рефлексии упадёт,
но `LightBlock t6 / ShadowCameras t7 / Camera t8` останутся на своих слотах — CPU просто
забиндит на один слот больше, чем шейдер читает. Вставка в СЕРЕДИНУ списка так не проходит:
это тот самый класс граблей, из-за которого в `skybox.frag.hlsl:36`, `menger.frag.hlsl:40` и
`mandelbrot.frag.hlsl:129` стоят якорные ветки.

**Блок 7. Константы через `ShaderDefine`.** Три константы, все объявляются в C++ один раз —
в `ShaderTypes.h`, рядом с `TextureSlotRole` и `ShaderDefine`: за ними придут и `BatchBuilder`
(нумерация `cell`, гарды переполнения), и `TextureStateDataModule` (страйд секции), и место
создания шейдеров.

| константа | что задаёт | значение |
|---|---|---|
| `MAX_SLOTS` | сколько слотов у шейдера → размер `slot_layout` | 12 (3 × `uint4`) |
| `MAX_VARIATIVE_SLOTS` | сколько слотов могут нести варианты → размер секции | 4 |
| `MAX_UVL_BLOCKS` | сколько блоков влезает в таблицу UVL → размер `textures[]` | 32 |

Набор дефайнов собирается там же, где объявлен дефолтный набор шейдеров, — в
`Engine::InitDefaultShaders` (`Engine.cpp:319`; отдельного `DefaultShaderSet.{h,cpp}` в отличие
от `DefaultCommandSet`/`DefaultRenderPassSet`/`DefaultUpdateSet` сейчас нет — если набор
когда-нибудь выделят в такой файл, константы дефайнов уезжают вместе с ним):

```cpp
const ShaderDefines kVariantDefines = {
    { "MAX_VARIATIVE_SLOTS", std::to_string(MAX_VARIATIVE_SLOTS) },
    { "MAX_SLOTS",           std::to_string(MAX_SLOTS) },
    { "MAX_UVL_BLOCKS",      std::to_string(MAX_UVL_BLOCKS) },
};
```

Набор отдаётся хвостовым параметром `CreateFragmentShader(..., defines)` КАЖДОМУ fs, который
включает пролог. Забыть один — он соберётся на дефолте `#ifndef`, без ошибки и без лога, и его
секции разъедутся с чужими.

```hlsl
#ifndef MAX_VARIATIVE_SLOTS
#define MAX_VARIATIVE_SLOTS 4
#endif
```

Дефайны входят в ключ кэша `.spv` (`ShaderManager::LoadOrCompileSPIRV`) и в `shaders.json`
(часть рецепта пересборки, см. `VertexShaderData::defines`), поэтому смена константы сама
инвалидирует кэш. Литерал в шейдере дублировать НЕЛЬЗЯ иначе как дефолтом `#ifndef`: разъезд
CPU и байткода тихо перемешает секции.

**Блок 8. Шейдеры.** `main_pass.vert.hlsl`: в `VSOutput` добавить
`nointerpolation int v_stateOfs : TEXCOORD6` = `InstanceDataBlock[row].state_offset`
(`row < 0` -> `-1`). Тот же член в `PSInput` трёх прологов (`main_pass/`,
`transparent_pass/`, `main_pass/untextured/`) на `vk::location(6)` — вершинник общий,
разъехавшийся `PSInput` = молча битые локейшены. В `main_pass/material_api.hlsl`:
`textures[MAX_UVL_BLOCKS]`, `cbuffer VariantLayoutBlock : register(b2, space3)` (см. блок 5),
`StructuredBuffer<int> TextureState : register(t9, space2)`, функция:

```hlsl
uint TexIndex(uint s)
{
    uint L     = slot_layout[s >> 2][s & 3];   // s — литерал, обе индексации статические
    uint count = L & 0xFFu;
    uint v = 0u;
    if (count > 1u && g_stateOfs >= 0)
        v = (uint)TextureState[g_stateOfs + g_sectionOfs + ((L >> 8) & 0xFFu)];
    if (v >= count) v = 0u;
    return (L >> 16) + v;
}
```

`g_stateOfs` (из интерполянта) и `g_sectionOfs` (= `material_index * MAX_VARIATIVE_SLOTS` —
единственное место, где нужен этот дефайн) — `static`, инициализируются базой до `getSurface`,
чтобы не менять сигнатуры `SampleAlbedo(uv)` и не ломать пользовательские `surface.hlsl`.

**Блок 9. API, команды, редактор.** `EngineContext::SetTextureVariant(e, mat_index, role, v)`
находит/вставляет пару в `MaterialRef.states`. Это правка поля НА МЕСТЕ, а не структурная
мутация: архетип не меняется, сущность не создаётся и не удаляется — значит ни
`SetDirtyBatches`, ни `QueueUpdate` не нужны, дерево батчей не трогается вовсе. Через команду
(`InputManager::PushCommand`) идти всё равно обязательно, но по другой причине: ECS мутирует
только sim-поток, UI шлёт команду и читает. Новые команды
`SetEntityTextureVariant`, `AddMaterialTextureVariant`, `RemoveMaterialTextureVariant`;
у существующей `SetMaterialTextureCmd` (`UI_Inspector.cpp:250`) появляется индекс варианта.
`UI_Inspector.cpp:245` — вместо комбобокса на роль список вариантов с `+`/`x`.
`UI_ComponentEditor` — спиннер варианта на слот.

## Инварианты и ограничения

- **Всё, что уходит в пуш, входит в ключ texture-батча** — точнее, всё, что шейдер по этой
  раскладке ЧИТАЕТ. После `3e47d7b` ключ не содержит идентичности материала, разные материалы
  схлопываются в один узел. Исключение ровно одно и оно измерено: `material_index` у узла без
  вариантов (`count == 1` везде) не читается — в ключ не идёт.
- **Все варианты одного слота — в одном атласе.** На слот биндится один `Texture2DArray`,
  UVL адресует слой внутри него.
- **Вариативная роль = роль с >1 текстурой; порядок ячеек = обход `Material::textures`**
  (`std::map`, по возрастанию `TextureSlotRole`). Считается независимо в двух местах — см. 4c.
- **Transformless-дровабл вариантов не получает** — у него нет строки трансформа, а состояние
  адресуется через `InstanceData[row]`. То же ограничение, что у per-instance `alpha`/`flags`.
- **`MAX_VARIATIVE_SLOTS` — одна константа на C++ и HLSL,** через `ShaderDefine`. Дублировать
  литералом нельзя.
- **Смена значения варианта — не структурная**; смена НАБОРА вариантов — структурная
  (`SetDirtyBatches`), UVL и раскладка копируются в батч значениями.
- **Потолок таблицы UVL** — пуш uniform-а ограничен ~16 КБ гарантированного минимума, то есть
  ~1000 блоков суммарно на материал. Рабочий потолок задан `MAX_UVL_BLOCKS` (32 = 512 байт) —
  размер `textures[]` это константа компиляции, одна на все материалы. Дальше таблица должна
  переехать из пуша в storage-буфер.
- **Разрядность полей слова:** `base` 16 бит (65535 блоков), `cell` 8, `count` 8 (255 вариантов
  на слот). Все с запасом относительно потолка пуша.
- **`InstanceData` 8 -> 12 байт** — +4 МБ/кадр на 1М объектов в буфере, который льётся без
  dirty-гейта.
- **Индекс блока слота в `textures[]` НЕ равен `s`** — только через `base`. Любой пролог,
  сэмплящий `textures[]` напрямую, обязан идти через `TexIndex`, даже если вариантов не ждёт:
  при их отсутствии формула вырождается в `s`.

## Отложено

- **Гейт заливки** state-буфера и префикса по dirty от правок материала/состояний
  (сейчас пересчёт каждый кадр).
- **Упаковка ячеек** в байты вместо `uint` на ячейку.
- **UVL-таблица в storage-буфере** при сотнях вариантов.
- **Чистка leftover-ролей** при `RemoveMaterialShader`.
- **Замер дробления батчей на сцене С вариантами.** Замер БЕЗ вариантов сделан (см. развилку
  про `variative`): дерево совпадает с базой. Сколько узлов добавит реальный вариативный контент
  — пока неизвестно, но платят только вариативные пары (материал, sp).
