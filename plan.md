# Переключаемые варианты текстур — план

Слот материала (например `Albedo`) держит **несколько** текстур; рисуется одна. Выбор —
**per-object** состояние, не per-material: два куба с одним материалом показывают разные
варианты и остаются в одном инстанс-батче.

Статус: часть 1 (слой данных) расписана, часть 2 (GPU) — конспектом.

## Терминология

Четыре уровня, которые легко перепутать:

| термин | что это | где живёт | гранулярность |
|---|---|---|---|
| **блок** | `UVL_Block` — где текстура лежит в атласе (uv offset/scale/layer) | пуш `uvl_push` | одна текстура |
| **элемент** | все состояния одной сущности | буфер `TextureState` | сущность |
| **секция** | часть элемента, относящаяся к одному материалу сущности; по ячейке на каждую РОЛЬ этого материала | буфер `TextureState` | (сущность, материал) |
| **ячейка** | один `uint` = номер выбранного варианта | секция | (сущность, материал, роль) |

```
ПУШ (uniform, собирается на пару ШЕЙДЕР + МАТЕРИАЛ — это и есть texture-батч)
  uvl_push[]     UVL_Block  -- где в атласе лежит каждая текстура
  slot_layout[]  uint       -- (base<<16)|(cell<<8)|count на слот шейдера
  slot_prefix    uint       -- сколько ячеек идёт до секции этого материала

БУФЕР InstanceData (storage, строка на объект)
  .state_offset  int        -- где в TextureState начинается элемент этой сущности; -1 = нет

БУФЕР TextureState (storage, один на всю сцену, ПЛОСКИЙ) -- НОМЕРА вариантов, ничего больше
  [ ... элемент энтити A ... | ... элемент энтити B ... ]
                                    |
                                    +- секция материала 0 : по ячейке на роль материала 0
                                    +- секция материала 1 : по ячейке на роль материала 1
```

Номер из ячейки уходит индексом в пуш: `uvl_push[base + номер]` — вот там уже настоящий UVL.

Одно и то же состояние живёт в трёх представлениях, каждое уместно на своём месте:

| где | чем адресуется | почему так |
|---|---|---|
| ECS (`MaterialRef.variants`) | по **роли**, разреженно | переживает правку набора ролей материала |
| буфер `TextureState` | по **ячейке**, плотно | без дырок и заполнителей |
| пуш `slot_layout` | **перевод** слот шейдера → ячейка | считается на пару (шейдер, материал) |

## Принятые решения и почему

Раздел существует, чтобы не переигрывать заново уже закрытые развилки.

**Состояние — per-instance канал, не пуш.** Пуш uniform-а работает на texture-батч, а батч
= один `SDL_DrawGPUIndexedPrimitivesIndirect` на тысячи инстансов. Per-object данные ходят
только через буфер, индексируемый строкой (`row`), как `Transforms`/`InstanceData`.
Вариант «состояние в ключ батча» отброшен: взрыв дерева + структурная пересборка на каждое
переключение.

**Раскладка таблицы UVL — сгруппированная по слотам,** дефолт = вариант 0 внутри группы.
Отдельная «плотная голова» из дефолтов рассматривалась и отброшена: групповая раскладка даёт
`idx = base + v` без `-1`, без константы N и без ветки на `v == 0`, а у материала без
вариантов вырождается в сегодняшнюю таблицу (`count` все единицы → `base[s] == s`).
Взамен — контракт: индекс блока слота НЕ равен `s`, любой пролог обязан идти через `base`.

**Пуш несёт `(base << 16) | (cell << 8) | count` на слот, а не сырые счётчики.** Сырые
счётчики требовали префиксной суммы в шейдере (0–3 сложения, `[unroll]`) и плохо
масштабировались на 10+ слотов (динамическая индексация `uint4[3]`). Упакованное слово
занимает те же 16 байт на 4 слота, убирает цикл целиком и вмещает `cell` и `count`.

**`cell` пушится, а не выводится шейдером.** `cell` — порядковый номер роли **среди ролей
материала** (не значение enum), поэтому дырок не бывает: у материала без ORM эмиссия получает
ячейку 2, а не 3. Шейдер такое вычислить не может — он не знает, какие роли у материала есть.
Зато пуш собирается на пару (шейдер, материал), потому что texture-батч лежит под конкретным
sp в дереве, — это и есть готовый шейдеро-специфичный канал.

Без этого ломались бы два реальных сценария:
- **leftover-роли.** `RemoveMaterialShader` (`DefaultCommandSet.cpp:235`) намеренно не чистит
  роли удалённого sp: «leftover-роли в textures не чистим — безвредны». Сегодня безвредны,
  потому что таблица UVL строится обходом `sp->required_slots`. С выводимым номером ячейки
  лишняя роль сдвинула бы нумерацию, и объект взял бы состояние соседнего слота — причём
  проявилось бы это не при правке, а на следующей загрузке сцены;
- **несколько sp у материала.** `AddMaterialShader` (`:225`) добирает роли нового sp, то есть
  набор ролей материала = ОБЪЕДИНЕНИЕ по всем его sp и не равен списку ни одного из них.

**Секции ЗУБЧАТЫЕ — по ячейке на каждую роль материала.** Вариант с фиксированным страйдом
`ROLE_CELL_COUNT` и нулями на несуществующих ролях отброшен: он требует канонического
глобального номера роли, тратит ячейки на роли, которых у материала нет, и всё равно не решает
ничего, чего не решает пушный `cell`.

**`slot_prefix` — в ключ texture-батча.** Это смещение секции внутри элемента, то есть сумма
числа ролей ПРЕДЫДУЩИХ материалов сущности. Величина per-entity: две сущности могут рисовать
один и тот же материал под одним `material_index`, но иметь разный набор соседних материалов
(`[wood(2 роли), metal]` против `[glass(4), metal]` → смещение 2 против 4). В пуш её как есть
не положить. Добавление `slot_prefix` в ключ батча делает её константой батча → едет обычным
пушем одним `uint`. Заодно `material_index` из ключа не нужен — он использовался только затем,
чтобы этот префикс проиндексировать.

Отброшенные альтернативы: заголовок со смещениями секций в начале элемента (лишнее зависимое
чтение буфера + `M` ячеек на элемент); довезти номер материала через каллинг
(`CmdMaterialIndex` + параллельный компактный выход скаттера — трогает `culling_pib.comp`
и сентинел `-1` в `out_pib`).

Цена принятого решения: сущности с одинаковым материалом, но разным по числу ролей набором
ПРЕДЫДУЩИХ материалов, разъезжаются на разные батчи. Лишний драв-колл на расхождение, не работа
на объект; при одинаковой раскладке материалов по моделям не разъезжается ничего.

**Компонент хранит состояния ПО РОЛИ, а не по номеру ячейки.** Номер ячейки сдвигается, когда
у материала меняется набор ролей; роль — нет. Хранить ячейку значило бы, что правка материала
молча переставляет состояния на соседние слоты.

**Сентинел «нет вариантов» = `-1`.** Буфер объявляется `StructuredBuffer<int>`, проверка `< 0`
— как `PIB_DataModule::kNoRow`. НЕ `uint` с `< 0`: это всегда false, молча.
Альтернатива «зарезервированный нулевой элемент + `prefix = 0`» убирает одну когерентную
ветку и читается хуже — отброшена.

**Гард `count > 1` и кламп `v >= count → 0` в шейдере обязательны.**
Гард: слот с одним вариантом состояние читать не должен — и потому что читать нечего, и потому
что у слота, которого у материала нет (подставлен dummy), ячейки не существует вовсе.
Кламп: таблица плотная, и при удалении варианта `count`/таблица пересчитываются, а номер в
компоненте — нет; `base + v` уехал бы в блоки СЛЕДУЮЩЕГО слота (нормалка сэмплится как альбедо
— правдоподобная неправильная картинка без строки в логе). Одно сравнение покрывает это, смену
материала, правку `materials.json` руками и любой транзиентный кадр. CPU-подрезка при удалении
варианта не нужна: дороже и не полная.

**Префиксная сумма пересчитывается каждый кадр.** Гейт по dirty от правок материала/состояний —
отложен (см. «Отложено»).

## Итоговая схема данных

```
МАТЕРИАЛЫ
  wood    Albedo = [alb_d, alb_1, alb_2]   Normal = [norm_d, norm_1]      2 роли
  metal   Albedo = [m_alb]                                                1 роль

СУЩНОСТЬ "стул"  materials = [ wood, metal ]        (порядок = submesh.material_index)
  элемент = секция wood (2 ячейки) + секция metal (1 ячейка) = 3 ячейки
  InstanceData[row].state_offset = 12
  TextureState[12..13] = состояния wood   (ячейка 0 = Albedo, 1 = Normal)
  TextureState[14]     = состояние metal  (ячейка 0 = Albedo)

TEXTURE-БАТЧ (шейдер Lit + материал wood, slot_prefix = 0)
  uvl_push    = [alb_d, alb_1, alb_2, norm_d, norm_1]
  slot_layout = [ (base=0, cell=0, count=3), (base=3, cell=1, count=2) ]
  slot_prefix = 0

TEXTURE-БАТЧ (шейдер Lit + материал metal, slot_prefix = 2)
  uvl_push    = [m_alb]
  slot_layout = [ (base=0, cell=0, count=1) ]
  slot_prefix = 2                       // до секции metal идут 2 ячейки wood
```

Адресация в пиксельном шейдере для слота `s`:

```
prefix_offset = InstanceData[row].state_offset          // -1 = вариантов нет
L             = slot_layout[s]
count         = L & 0xFF
v             = (count > 1 && prefix_offset >= 0)
                ? TextureState[prefix_offset + slot_prefix + ((L >> 8) & 0xFF)]
                : 0
v             = (v >= count) ? 0 : v                    // кламп протухшего
uvl           = uvl_push[(L >> 16) + v]
```

**Ключевые свойства.** Материал без вариантов → `count == 1` везде, `base[s] == s`, таблица
байт-в-байт сегодняшняя, у всех сущностей `state_offset == -1`, буфер состояний не читается:
нулевая регрессия. Смена варианта — запись в компонент, дерево батчей не трогается.
Смена НАБОРА вариантов или ролей — структурная, требует `SetDirtyBatches`.

# ЧАСТЬ 1 — слой данных

После этой части буферы заполнены правильными данными, но шейдер их не читает: поведение
движка не меняется ни на пиксель.

## Блок 1. `Material`: слот-роль → вектор имён

**`MaterialData.h`**

```cpp
struct Material {
    // Слот держит СПИСОК текстур: [0] — то, что рисуется по умолчанию, дальше варианты,
    // переключаемые состоянием на сущности. Пустой вектор = слота у материала нет.
    // std::map, а не unordered_map: порядок ролей задаёт нумерацию ячеек состояний,
    // и он обязан быть детерминированным — его независимо считают BatchBuilder и модуль
    // заливки.
    std::map<TextureSlotRole, std::vector<TextureName>> textures;
    ...
};
```

**`MaterialManager::CreateMaterial`** — тип параметра `vector<pair<role, vector<TextureName>>>`.

**`MaterialManager::CollectSamplerUsage`** — обходит ВСЕ элементы вектора. Пропустишь — атлас
редкого варианта не получит `SDL_GPU_TEXTUREUSAGE_SAMPLER`, и сломается не здесь, а на первом
кадре, где этот вариант включили (`WARNINGS.md`, поздний usage-флаг).

**`EngineContext::CreateMaterial`** (`EngineContext.cpp:170`) — тип в `initializer_list`;
к существующей валидации `required_slots` добавляется проверка **«все варианты одного слота
лежат в одном атласе»** (варнинг, не отказ). Причина: на слот биндится один `Texture2DArray`,
UVL адресует слой внутри него — вариант из чужого атласа переключить нечем.

**Сериализация** — `Engine_Scene.cpp:402` (save) / `:701` (load), плюс `MaterialEntry` (`:705`):

```json
"textures": [ { "role": "Albedo", "textures": ["wood_d", "wood_cracked"] } ]
```

Чтение старого формата (`"texture": "имя"` скаляром) даёт вектор из одного элемента —
существующие сцены не переписываются.

## Блок 2. `MaterialComponent`: имя + состояния

**`BaseComponents.h`**

```cpp

// variants РАЗРЕЖЕННЫЕ и ПО РОЛИ, а не по номеру ячейки в буфере: номер ячейки зависит от
```

## Блок 3. `BatchBuilder`: ключ батча, таблица UVL, раскладка слотов

### 3a. Префикс секций сущности

В начале `AddEntityToBatches`, ДО цикла по сабмешам, считается массив смещений секций —
по одному на материал сущности:

```
roles(j)     = число ролей материала j (0, если имя не резолвится)
slot_prefix[i] = sum roles(j) для j < i
```

Один раз на сущность, а не на сабмеш. Модуль заливки (блок 4) обязан считать это ТЕМ ЖЕ
способом, включая обработку неразрешимого имени.

### 3b. Ключ texture-батча

**`BatchBuilder.cpp:46`**

```cpp
TextureBatchKey HashTextureBatchKey(const Material* mat, uint32_t slot_prefix);
```

Сейчас ключ — идентичность материала (`&mat->params`). Добавляется `slot_prefix`, потому что он
уходит в пуш, а пуш обязан быть константой батча (обоснование — в «Принятых решениях»).

### 3c. Сборка таблицы UVL и раскладки слотов

**`BatchBuilder.cpp:312`** — один проход по `sp->required_slots`, для каждого слота подряд все
его варианты, дефолт первым. Бегущий счётчик записанных блоков и есть `base`:

```
uvl = [ alb_d, alb_1, alb_2, norm_d, norm_1, em_d ]
        \_ Albedo _______/  \_ Normal _/  \_Emis_/
```

Для каждого слота `s` пишется слово:

| поле | биты | что | как считается |
|---|---|---|---|
| `base` | 16 | индекс первого блока слота в `uvl_push` | бегущий счётчик блоков |
| `cell` | 8 | ячейка секции, где лежит состояние слота | сколько ролей материала идёт до этой роли (обход `std::map`) |
| `count` | 8 | сколько у слота вариантов | фактически собранное число блоков |

`count` — ФАКТИЧЕСКИ собранное, а не `material->textures[role].size()`. Вариант с неразрешимым
именем в таблицу не попадает и счётчик уменьшает; иначе базы всех последующих слотов
разъедутся. Дефолт при промахе подменяется dummy и место сохраняет.

Слот, которого у материала нет вовсе (dummy на весь слот): `count == 1`, `cell` не используется
— пишется 0.

### 3d. Что кладётся в батч

**`RenderCommandData.h`**

```cpp

    uint32_t slot[MAX_SLOTS];   // MAX_SLOTS = 12 (3 x uint4 в пуше)
    uint32_t slot_prefix;       // смещение секции этого материала внутри элемента
};

struct TextureBatchData {
    std::vector<UVL_Block> texture_uvl;

```

**`RenderSnapshot.h:38`** — `RenderSnap::TextureDraw` получает копию `VariantLayout` рядом с
копией `texture_uvl`: рендер читает только слепок.

**`HashAtlasBatchKey`** (`:61`) — хэшировать `textures[role][0]`; остальные варианты по
инварианту в том же атласе, в ключ не входят.

## Блок 4. Заливка

### 4a. `InstanceData`

**`InstanceDataModule.cpp:7`** (`DrawComponent` не трогается — поле вычисляемое):

```cpp
struct InstanceData {
    float    alpha;
    uint32_t flags;
    int32_t  state_offset;   // -1 = вариантов нет; иначе начало элемента в TextureState
};
```

8 -> 12 байт. Правки в `CalculateInstanceSize` и в цикле `StoreInstanceData`.

### 4b. Буфер состояний

- `DEFAULT_TEXTURE_STATE_BUFFER` в `BufferManager.h:24`, создание в `BufferManager.cpp:15`;
- модуль `TextureStateDataModule` (size + store) по образцу `InstanceDataModule`;
- `SetDefaultTextureStateUpdater` в `DefaultUpdateSet`, вызов из `Engine.cpp:461`.

Элемент сущности = конкатенация секций в порядке `materials`. Секция материала = по ячейке на
каждую его РОЛЬ, в порядке `std::map` (тот же порядок, по которому `BatchBuilder` считал
`cell`). Ячейка = номер варианта из `MaterialRef.variants` по этой роли, 0 если роли там нет.

Элемента НЕТ вовсе, если ни у одного материала сущности нет непустого `variants`.

```
running = 0
для каждой строки {Positions, DrawComponent}:
    mc = MaterialComponent, если есть у архетипа
    если !mc или все variants пусты:
        instance[row].state_offset = -1
        продолжить
    instance[row].state_offset = running
    для каждого m из mc->materials:
        mat = резолв m.name
        для каждой роли mat->textures по порядку:
            state[running++] = m.variants[роль] либо 0
```

Модулю нужен `MaterialManager`, чтобы резолвить имя → число ролей. Он приходит **параметром**
из замыкания update-инструкции (как `om`/`bm` сейчас), полем НЕ хранится — см. CLAUDE.md.

### 4c. Опциональный компонент в обходе — правка ядра

`ForEachArchetype<Ts...>` требует все компоненты обязательными. Домен строк —
`{Positions, DrawComponent}`; `MaterialComponent` есть не у всех таких архетипов (сущность с
позицией и Draw, но без материала, строку занимает, просто не рисуется). Если добавить его
третьим обязательным, часть строк выпадет и бегущий префикс разъедется с нумерацией строк.

**Правка:** `ForEachArchetype<Positions, DrawComponent, Opt<MaterialComponent>>`, отдающий
`nullptr` для архетипов без него. Локальная шаблонная развязка в `ObjectManager.h`; тот же
паттерн понадобится любому следующему опциональному per-instance каналу.

Обходной путь без правки ядра — два прохода с ключом по указателю
`ComponentArray<DrawComponent>*` — это «второй индекс сбоку», от которого отговаривает
CLAUDE.md.

### 4d. Инвариант, который надо закомментировать

Есть ТРИ места, независимо считающие одну и ту же раскладку:
`BatchBuilder` (для `cell` и `slot_prefix` в пуше), `InstanceDataModule` (для `state_offset`)
и `TextureStateDataModule` (для самих секций). Расходиться им нельзя.

Два модуля — РАЗНЫЕ update-инструкции (`CreateUpdateInstruction` заводится на имя буфера, одна
инструкция два буфера не пишет). Согласованы они только потому, что обе — детерминированные
функции одного и того же ECS + одних и тех же материалов, а те между ними не мутируют: обе идут
на sim-потоке в одной фазе prepare. Пуш согласован потому, что дерево батчей пересобрано до
заливки.

Вынос любого из трёх в другой поток или под отдельный dirty-гейт даст разъехавшиеся смещения —
без краша, без лога, просто чужие варианты у части объектов. Комментарий во всех трёх местах +
раздел в `WARNINGS.md`.

Практический вывод: порядок ролей берётся ТОЛЬКО обходом `Material::textures` (`std::map`),
неразрешимое имя материала трактуется как 0 ролей — одинаково везде.

# ЧАСТЬ 2 — GPU (конспект, детализировать)

**Блок 5. Пуш в `ExecuteRenderBatches`** (`RenderManager.cpp:~428`). Третий fragment-uniform
ПОСЛЕ params, чтобы не двигать `MATERIAL_BLOCK_REGISTER`: `b0` uvl, `b1` params,
`b2` variant layout (`uint4[ceil(N/4)]` слов + `slot_prefix`). Гейт по `frag_uniform_count`,
как у params; логика «плотных слотов» становится трёхступенчатой — вынести в хелпер.

**Блок 6. Регистрация `TextureState` у sp.** Имя в КОНЕЦ `fragment_shader_buffer_names` тех sp,
которым нужны варианты (`Engine::InitDefaultShaders`, `Engine.cpp:382`/`389`/`399`). Хвостовое
добавление не сдвигает `LightBlock t6 / ShadowCameras t7 / Camera t8` — получит `t9`.
Shadow/depth-sp не получают.

**Блок 7. Шейдеры.** `main_pass.vert.hlsl`: в `VSOutput` добавить
`nointerpolation int v_stateOfs : TEXCOORD6` = `InstanceDataBlock[row].state_offset`
(`row < 0` -> `-1`). Тот же член в `PSInput` трёх прологов (`main_pass/`,
`transparent_pass/`, `main_pass/untextured/`) на `vk::location(6)` — вершинник общий,
разъехавшийся `PSInput` = молча битые локейшены. В `main_pass/material_api.hlsl`:
`textures[64]`, `cbuffer VariantLayoutBlock : register(b2, space3)`,
`StructuredBuffer<int> TextureState : register(t9, space2)`, функция:

```hlsl
uint TexIndex(uint s)
{
    uint L     = slot_layout[s >> 2][s & 3];   // s — литерал, обе индексации статические
    uint count = L & 0xFFu;
    uint v = 0u;
    if (count > 1u && g_stateOfs >= 0)
        v = (uint)TextureState[g_stateOfs + slot_prefix + ((L >> 8) & 0xFFu)];
    if (v >= count) v = 0u;
    return (L >> 16) + v;
}
```

`g_stateOfs` — `static int`, инициализируется базой до `getSurface`, чтобы не менять сигнатуры
`SampleAlbedo(uv)` и не ломать пользовательские `surface.hlsl`.

**Блок 8. API, команды, редактор.** `EngineContext::SetTextureVariant(e, mat_index, role, v)`
находит/вставляет пару в `MaterialRef.variants`; вставка — структурная мутация, значит только
командой (`InputManager::PushCommand`), не с UI-потока. Новые команды
`SetEntityTextureVariant`, `AddMaterialTextureVariant`, `RemoveMaterialTextureVariant`;
у существующей `SetMaterialTextureCmd` (`UI_Inspector.cpp:250`) появляется индекс варианта.
`UI_Inspector.cpp:245` — вместо комбобокса на роль список вариантов с `+`/`x`.
`UI_ComponentEditor` — спиннер варианта на слот.

## Инварианты и ограничения

- **Все варианты одного слота — в одном атласе.** На слот биндится один `Texture2DArray`,
  UVL адресует слой внутри него.
- **Порядок ролей = обход `Material::textures`** (`std::map`, по возрастанию
  `TextureSlotRole`). Он задаёт нумерацию ячеек и считается независимо в трёх местах — см. 4d.
- **Смена значения варианта — не структурная**; смена НАБОРА вариантов или ролей — структурная
  (`SetDirtyBatches`), UVL и раскладка копируются в батч значениями.
- **Потолок таблицы UVL** — пуш uniform-а ограничен ~16 КБ гарантированного минимума, то есть
  ~1000 блоков суммарно на материал. Дальше таблица должна переехать из пуша в storage-буфер.
- **Разрядность полей слова:** `base` 16 бит (65535 блоков), `cell` 8 (255 ролей),
  `count` 8 (255 вариантов на слот). Все с запасом относительно потолка пуша.
- **`InstanceData` 8 -> 12 байт** — +4 МБ/кадр на 1М объектов в буфере, который льётся без
  dirty-гейта.
- **Индекс блока слота в `textures[]` НЕ равен `s`** — только через `base`. Любой пролог,
  сэмплящий `textures[]` напрямую, обязан идти через `TexIndex`, даже если вариантов не ждёт:
  при их отсутствии формула вырождается в `s`.
