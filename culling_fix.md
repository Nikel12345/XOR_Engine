# Каллинг: пер-групповая раскладка индиректа и out_pib

Статус: РЕАЛИЗОВАНО (ветка komp). Ниже — что и почему, включая две поправки к исходному плану.

## Проблема

Индирект и out_pib были декартовым произведением камер на содержимое всех проходов:
`(1+L) * TC` команд и `(1+L) * N` записей. Камера же принадлежит ровно одной группе
проходов, поэтому в блоке теневой камеры лежали main-команды, в блоке игрока — теневые,
и всё это чистилось и переливалось каждый кадр.

Стало: `сумма по группам (камеры_группы * команды_группы)`.

## Раскладка

Пример из смоук-теста: теневой проход 10 команд / 22 записи, группа игрока (main +
transparent + debug + UI) 16 команд / 30 записей, 4 теневые камеры.

    индирект:  [ игрок: 1 блок по 16 ][ свет: 4 блока по 10 ]   = 56 команд (было 5*26 = 130)
    out_pib:   [ игрок: 1 блок по 30 ][ свет: 4 блока по 22 ]   = 118 int  (было 5*52 = 260)

В `first_instance` команды лежит АБСОЛЮТНЫЙ адрес её куска в out_pib:

    fi = pib_base(группы) + номер_камеры * pib(группы) + локальное_смещение

Локальное смещение накапливается при обходе группы, вычитаний нет нигде. Поскольку
`SV_InstanceID = first_instance + i`, оба вершинника читают `OutPib[instanceID]` без
арифметики блоков.

## Две поправки к плану

**1. Индекс команды локален для ГРУППЫ, а не для прохода.** В группе игрока проходов
несколько (main/transparent/debug/UI), и они делят один регион — при пер-проходной
нумерации их команды столкнулись бы. Для теневой группы (один проход) разницы нет,
поэтому на примерах это не всплывало.

**2. Связь «проход - камеры» не живёт ни на проходе, ни в ядре.** Первая попытка была тегом
`RenderPassStep::camera_group` — неверно дважды: проход не должен знать о камерах, а тег
дублирует порядок проходов. Правильное разделение: «какие проходы делят один регион команд»
(нужно ядру, о камерах ни слова) и «сколько камер у региона» (о камерах, ядру не нужно).

Первое — `RenderSnap::GroupSpan { first_pass, pass_count }`. Прогоны объявляет набор проходов
(`BuildCameraGroupSpans`, он знает и про SHADOW_PASS, и про световые камеры), один раз после
`FillRenderPasses`, и они инжектятся в `BatchBuilder`. Тот нумерует по ним команды и кладёт
их же в `BatchLayout::groups` — поэтому нумерация и регионы физически из одного источника и
разойтись не могут. Второе (число камер) приходит от `LightDataModule` прямо в `BuildRegions`.

## Что сделано

- `RenderSnap::GroupSpan` + `BatchLayout::groups` + `GroupOfPass` (`RenderSnapshot.h`) —
  прогоны проходов, делящих регион; хранятся вместе с раскладкой, которую по ним и
  пронумеровали. Читатели (`BuildRegions`, `StoreIndirect`, `StoreEntityToCmd`) берут их
  оттуда, а не вычисляют заново.
- `DefaultRenderPassNamespace::BuildCameraGroupSpans(pm)` — ЕДИНСТВЕННОЕ объявление связи
  «проход - камеры»; зовётся один раз в `Engine` сразу после `FillRenderPasses`, результат
  инжектится в `BatchBuilder::SetCameraGroupSpans`. Позицию теневого прохода спрашивает у
  реестра обходом, а не у самого прохода.
- `RenderSnap::Region/Regions/BuildRegions` (`RenderSnapshot.h`) — раскладка регионов из
  слепка; порядок регионов (= порядок group id) задан только здесь. Группа 0 — игрок,
  поэтому её база всегда 0 и нетеневые проходы рисуют со смещением 0, как раньше.
- `DefaultRenderPassNamespace::AskRegions(bb, ldm, slot)` — ЕДИНСТВЕННЫЙ способ получить
  регионы слота; зовут size-фазы обоих буферов, пуши трёх compute-программ и теневой дроу.
- `PassDrawList` получил `num_commands`; `indirect_command_index` в слепке и значения
  `EntityToCmd` стали локальными для группы (`BatchBuilder`, `PIB_DataModule`).
- `IndirectDataModule` пишет регионами с ребейзом `first_instance` и сел на гейт
  `{BatchesRevision, число теневых камер}` per slot.
- `culling_pib.comp`: `CullParams` = {range_start, range_count, num_blocks, cmd_base,
  commands}; адрес команды = `cmd_base + b*commands + k`, адрес out_pib берётся из самой
  команды. Ушли `block_base`, `block_stride`, `total_commands`.
- `culling_clear.comp`: без изменений по сути, `total_slots` = сумма по группам.
- `shadow_pass.vert`: `OutPib[instanceID]`; из `ShadowPushData` ушло поле `num_instances`.
- Удалено как осиротевшее: `ShadowPib`, `BatchBuilder::AskNumCommands/AskNumInstances`,
  `BatchLayout::num_commands/num_instances`, `IndirectDataModule::AskNumCommands`.
  Суммы по всей раскладке больше не ответ ни на один вопрос — все они пер-групповые.

## Инварианты и грабли

- **Вся адресная арифметика — только сложения и умножения, ни одного вычитания.**
  Беззнаковое вычитание молчит и в шейдере (нет ассертов), и на CPU, а промах даёт запись
  в чужой регион. Держится на локальных индексах команд и накопительном счётчике смещения.
- **Проходы одной группы обязаны идти подряд по pass_index.** Регион группы непрерывен и в
  командах, и в PIB; второй прогон той же группы сдвинул бы её PIB-сегмент и разъехался с
  диапазоном culling-программы. Сейчас это выполняется (теневой проход первый), а
  `BuildCameraGroupSpans` громко логирует, если он перестал быть первым.
- **`culling_clear` обязан быть shader_batch[0] в CULLING_PASS** (`WARNINGS.md`), то есть
  создаваться первым в `SetCullingPibPrograms`.
- **L для адресов — неклэмпнутый.** В теневой лямбде есть `if (num_cams > max_layers)`
  (8 слоёв); он ограничивает только отрисовку. Регион считается по полному числу камер.
- **Проход с собственными камерами обязан попасть в прогон.** Не покрытый ни одним прогоном
  проход отходит группе 0 (исторический дефолт — камера игрока, см. `GroupOfPass`). Для
  обычного прохода это верно, для прохода со своими камерами — молча неверно: его записи всё
  равно обработает скаттер игрока. Лечится строкой в `BuildCameraGroupSpans`.
- **Команда с нулём инстансов носит бессмысленный `first_instance`** — может указывать в
  чужой регион, это нормально (GPU не заведёт ни одного инстанса). Не валидировать.
- `SV_InstanceID` включает `first_instance` в Vulkan (в D3D12 — нет). Зависимость была и до
  этой правки; комментарий стоит в `IndirectDataModule`.

## Проверка

Сделано:

1. Сцена с 4 теневыми камерами, Debug: 60 FPS, ноль ошибок/ассертов в логе.
2. Размеры по логу: индирект 1120 Б (56 команд) против 2600 Б (130), out_pib 118 int
   против 260.
3. Гейт индиректа: `.store` n=3 за первые 601 кадр (по одному разу на слот) и n=0 за
   следующие 600. Была заливка каждый кадр.
4. Шейдеры перекомпилировались (кэш инвалидируется по исходнику).

Осталось:

5. **Глазами**: тени на месте, объекты не пропадают и не дублируются. Автоматически это
   не проверяется — `Engine::DebugReadbackOutPib` из прежних сессий в коде больше нет.
6. Сцена БЕЗ теневого света (L=0) — регион света пуст, база игрока 0.
7. Добавить/убрать теневой свет на живой сцене — бьёт именно по новому гейту {ревизия, L}.
8. 1М кубов — дублей нет, FPS не хуже.
